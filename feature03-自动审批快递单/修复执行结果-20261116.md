这一时序会等待在飞请求超时，不能将请求超时简单相加为串行 60 秒，也不能据此解释旧 run 数分钟存活的全部机理。旧 run 原始证据保留，完整机理仍未定；本次没有为未复现的额外机理继续改生产代码。

## 可见审批窗口加载卡顿（15:26 首个真实新单，同日修复）

现象与根因：15:26 捕获首个真实新单后，主循环在 `ApprovalWindow.open` 同步阻塞 4 分 20 秒（[watcher 事件](../automation/runs/approval-watch-3a8eaca26323/events.jsonl) 行 1462–1464：15:26:25 `request_guard_ready` 后约 25 轮 cycle 空白，15:30:45 恢复 `opened=1`；期间零失败/零拦截/零 WS 事件）。根因：可见提醒窗口复用了业务探测的全量 `route.fetch` 中转守卫，首开详情页所有请求双重中转且 HTTP 缓存被禁用，加载被放大到分钟级并卡住主循环。不是上午修复的回归；上午矩阵中"真实后续新单提醒"本就待验，本次即其首次真实检验结果。

修复：`ApprovalWindow` 改用普通 context（`_new_visible_context`）——保留 `ignore_https_errors=False`、`service_workers="block"`、viewport、storage_state、浏览器级 `--no-proxy-server`、后台核实 URL 与打开后账号核对；不再装请求级守卫，页面行为与人工打开等价，并新增 `approval_window_context` 事件留痕。业务探测/填报入口的 guarded context 不变；`close()` 沿用既有无守卫分支。附带消除可见窗口关闭时 `unroute_all(wait)` 的等待；后台 context 清理等待保留。

回归：[watch 登录测试](../tests/test_approval_watch_login.py) 17 项（含新增 2 项锁定普通 context 路径与不走 `_new_guarded_context`）、[网络恢复测试](../tests/test_approval_network_recovery.py) 17 项通过；[退出测试](../tests/test_network_shutdown.py) 2 项通过（首次整组跑 polling 用例 65 秒看护超时一次，单独与整组复跑均通过，`shutdown_seconds≈30.0`，与上午"首次尝试偶发"模式一致，未为此改生产代码）。改后尚未有真实新单首开复验，待验。
