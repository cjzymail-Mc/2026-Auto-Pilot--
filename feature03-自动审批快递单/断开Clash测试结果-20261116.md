## 退出清理链阶段标记与旧卡点定位

本轮给 worker 打的桩：`set_offline → unroute_all(wait) → context.close → browser.close →（_pw.stop）→ _close_browser → release_lock`。两轮实测：

- `set_offline` 0.01–0.02s；`unroute_all(behavior="wait")` **0.00s**；`context.close` 0.03s；`browser.close` 0.11–0.14s；`_close_browser` 合计 0.19–0.24s；`release_lock` 0.00s；faulthandler 未触发（两日志 0 行）；worker 进程正常退出。
- 已知观测局限：`playwright_stop` 类级打桩未生效（`sync_playwright().start()` 返回对象未走被 patch 的静态类属性；其余 6 个阶段均有效）。其耗时被 `_close_browser` 合计覆盖，不影响"无卡点"结论。
- **旧卡点（run `approval-mode-clash_off-e8a23d171cb8`）对照**：`stopped` 10:03:49 后出现两个 `ams.api.qiaodan.com` 的 30 秒 `route.fetch` 超时（10:03:57、10:04:03），之后无任何事件、进程存活持锁直至被用户取消。与"`ContextGuard.close` 的 `unroute_all(wait)` 等待 closing 前已在飞的慢 fetch"一致：这两个 fetch 起始时间恰在 monitor 启动前后（~10:03:27/10:03:33）。
- **诚实结论**：本次两轮在 KeyboardInterrupt 时点无 30 秒级在飞 fetch，退出链亚秒完成，**未复现卡住**；上述机制只解释旧 run ≥60 秒的收尾延迟，不能完全解释其后数分钟仍存活——10:04:03 之后的卡点无事件证据，**完整机理未确定**。是否仍会复现：时序条件（停止时有长在飞 fetch 等 `unroute_all(wait)`）存在即可能复现；本日已部署的 180 秒外层硬超时 + faulthandler 留栈 + 阶段标记可在复现时给出准确阶段。
