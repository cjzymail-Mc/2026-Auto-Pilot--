先从真实观察确认主站、静态资源、认证服务（包括已观察到的公司认证依赖）和允许的企微扫码资源哪些是关键依赖。不要将所有公司子域都设成必须成功，也不要遗漏必要认证域。以实际 `ContextGuard._fetch` 的传输路径增加无凭证验证；Python socket 握手只能作为旁证，不能替代 Node/Chromium 的 DNS、证书和请求行为。

对于“不开 Clash”与“Clash 已开”分别留实际出口证据。当前监控仍在工作时，先完成离线修复；网络开关实验与原执行者协调后进行，不在两个 session 中同时操纵。若本轮不能取得关 Clash 的真实环境，只能写“该场景待验”，不得用环境 mock 代替。

### 2. 做最小的直连处理

- 应用层：保留 `--no-proxy-server`，核对 context/APIRequest 未引入 proxy；如实测环境变量影响 driver，仅在本工具进程/子进程隔离，不改用户全局代理环境。
- 系统代理/PAC：本工具应直接连接已允许域名，不以连接本机 Clash 代理端口作为“绕过”。检测到 Clash 运行本身不应阻断正常直连。
- DNS：先证实故障类型。若残留 fake-IP、环回 DNS 服务依赖或公司 split DNS 是根因，选择与公司网络相符的恢复；不能把换公共 DNS、硬编码历史 OA IP、改 hosts 或关闭 TLS 作为通用补丁。Python 预检中的 DNS 修复必须与实际 Playwright 请求链一致，单修预检不算解决。
- TUN：普通 proxy bypass 不等于绕过系统隧道。核对运行时生效的配置和目标路由；优先复用既有公司域规则及 DNS 例外，并验证规则优先级和 global/rule 模式含义。如确需修改，仅做与本工具企业域相关的可回滚最小增量；不覆盖订阅、不切换全局模式、不改变无关应用路线。按当前权限执行，受阻时记录具体权限和未完成项，不伪报自动修复。
- 无论采用何种方案，必须保留域/TLS/重定向/WebSocket 拒绝边界；不能将 `route.fetch` 换成无检查的 `route.continue()` 来躲避问题。

不得为尚未复现的环境分支引入自建代理、通用 VPN 管理器或大规模网络重构。若真实直连已经正常，仅对已证实的错误分类/恢复缺陷做代码修复，并把“早上底层网络原因未确定”写清楚。

### 3. 修正登录和运行状态转换

推荐显式阶段：网络诊断 → 复用认证 → 必要时等待扫码 → 扫码成功后的后台交接 → 任务中心就绪 → 持续监控。

每次网络尝试有自己的故障记录、截止时间和退避；DNS/TCP/TLS 等暂时错误可重试，真实身份冲突、真实 401/403、本地期限到期和守卫拒绝分别进入对应安全停点。不能将所有 `BrowserError` 都归为网络，不能在证书错误后降低验证。扫码等待预算与网络恢复预算分别计算，用户已扫成功后不因后台网络抖动要求重扫。

保持 600ms 分类轮询和原认证期限；登录/初始化阶段有时限，任务中心真实就绪后继续全天监控。恢复时仅重建本工具拥有的后台页面，保持已打开的可见详情页及去重状态；账号失效或改变时停操作并保留待处理窗口，不迁移旧账号任务。

### 4. 清理与测试

为每个自有 context 明确 guard 归属，避免 `probe._request_guard` 被可见窗口新 context 覆盖后误用于后台诊断。退出时标记 closing，阻断新流量，等待/结束已有 handler，依次关闭 context、browser、driver，最后释放本进程的锁。对未使用 guard 的公共调用保留兼容；不要仅为本工具消除异常而无验证地改变全部填报入口。
