# 寄件快递单自动审批

核对日期：2026-11-17。用户明确授权的范围是页面业务类型“快递单”的寄件业务，不是报销单中的“快递费”；用户同时要求正常弹出并展示 6 秒后流转。

## 使用方式

正常双击本目录的 [approval_watch.py](approval_watch.py)。完成当前账号登录核验后，默认进入自动审批状态，无需新增配置开关。监视窗口显示：

> 自动审批：仅寄件快递单，弹出展示 6 秒后流转；其他单据人工处理。

也可从仓库根执行：

```powershell
python -X utf8 "feature03-自动审批快递单/approval_watch.py"
```

已经运行的 Python 进程不会热加载磁盘代码。现有监控退出后，下次启动才使用新增功能；不要同时启动第二个实例或删除 profile 锁。退出时先处理现有人工审批窗口，再在监视窗口按 Ctrl+C。

## 实际行为

1. 后台按原间隔查询当前账号待审任务，所有新单仍走任务中心“查看”的正常打开流程。
2. 仅精确匹配 `/oa/express`，且页面是 `qd-express-detail`、页内单号与任务一致、快递明细已加载、流转按钮唯一可用，才进入自动处理。页面异步加载有有限等待。
3. 将单据显示在前台，使用单调时钟计满 6 秒。期间页面关闭、切换到其他标签、内容/账号变化或出现额外对话框，会停止本次自动处理。
4. 再核实当前身份、认证期限、原待办与页面内容，通过一次精确“流转”打开正常流转窗口。等待系统加载执行人，沿用唯一默认下一节点，通过窗口内一次精确“流转”确认。没有默认节点、多个未选节点、必填校验或额外确认时，保留页面人工处理；不自动填写、改选人员、点“结束”或“回退”。
5. 只有观察到对应业务 UUID 的正常成功响应、且重新从任务中心查询确认原待办消失，才显示“流转成功”。无法证明时显示“结果待核实”，不把点击或 HTTP 200 单独当作成功。
6. 非快递单保持弹出人工处理，不会因标题中含“快递”或报销类别是“快递费”而自动审批。

监视窗口的成功记录含时间、单号、明细行数，以及最多 3 项可读的物品名称/数量。例如以下均为合成数据：

```text
[16:00:00] 【流转成功】快递单 SHIP-SYNTHETIC-001｜明细 1 行｜测试样品 × 2
```

没有可读物品列时保留单号与行数。记录不包含收件人地址、电话、银行资料或认证信息。

## 意图、结果与扩展

实现位于 [bpm/approval.py](../bpm/approval.py)。每个账号/业务 UUID/待办 UUID 形成独立哈希键，在 Git 排除的 `automation/approval-registry/<key>.jsonl` 追加本机记录。首次点击前独占创建并 `flush/fsync`；正常顺序是 `FLOW_INTENT → FLOW_CONFIRM_INTENT → SUCCESS`，异常追加 `UNCERTAIN`。已有文件（包括不完整文件）阻断重放；记录失败时保留先前意图，不能删除账本来强行重试。

运行事件仍在 `automation/runs/approval-watch-*/events.jsonl`，新增 `approval_auto_display`、`approval_auto_result`；只记哈希任务键、状态和脱敏原因。后台原发现/周期日志及控制台快速编辑修复继续有效。

扩展入口是 `AUTHORIZED_HANDLERS` 与类型处理器的 `wait_ready/snapshot` 接口。当前仅登记 `ShippingHandler`；未来须先取得用户对新类型的明确授权，再实现独立类型/页面核验并加入登记。新增路由、名称或报销配置不会自动启用审批。

## 验证依据与限制

- 最终版本已通过 **72 项相关回归**，包括 7 项隔离 Chromium DOM 测试：真实浏览器本地页面的延迟加载、完整 6 秒、两步按钮操作、明细记录与跨实例不重放；身份/内容变化、用户关页、隐藏页面、未知弹框、节点变化、响应不匹配、磁盘失败、其他类型人工处理等分支。
- `stage1_probe_selftest.py` 已通过。原始输出与机器摘要在 [本轮离线验证目录](../automation/offline-verify/20261117-shipping-auto/summary.json)。测试使用合成数据，所有浏览器请求拦截在本机，不读取真实 profile、不连接 OA、不执行真实流转。
- 全量回归 **633 项：578 通过、18 失败、33 错误、4 跳过**。51 个失败/错误名称均在 11 月 16 日清单内；按原分类分别是缺 jsonschema 8 项、缺历史计划 8 项、PDF 提取/计划链 35 项，原长路径 24 项本轮未复现。见[逐项比对](../automation/offline-verify/20261117-shipping-auto/full-failure-comparison.json)；不宣称仓库全绿或已修复这些历史缺口。
- 全量在最后的表格可见性兼容调整前执行，源码快照单独保留；最终 72 项相关回归覆盖该调整及新增两个用例。新增零尺寸用例的前两轮曾因对浏览器布局/可见性规则的假设失败，最终改为显式设置零尺寸、单独核实可见子行，失败输出原样保留；最终源码哈希与各轮结果见[可交接摘要](自动审批验证-20261117.json)。
- 类型组件、快递明细、标准流转窗口、默认执行人及响应流程，核对了当日 OA 未认证可读取的公开前端代码；原始 bundle 仅保留于本机忽略目录 `automation/runs/approval-auto-discovery-20261117/`。没有直接调用写接口或访问 Angular 内部对象。
- **尚未完成真实快递单自动流转首验。** 当前运行的是旧进程，本轮未强停它、关闭已有业务窗口或并行占用 profile；隔离 DOM 测试不能替代真实 OA 验收。真实页面若与已核对结构不符，控制器会保留窗口并提示原因。
- VPN/Clash 的既有直连改动与[控制台暂停修复](控制台暂停修复-20261117.md)保持原有验证范围；TUN/fake-IP、整日运行及本轮真实新单到达仍不能由上述测试替代。
