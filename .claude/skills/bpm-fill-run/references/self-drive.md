## 接单、身份与路由

用户只给原件/公里表、参考单完整编号及执行意图。由 agent 生成内部数据；不让用户判内部类型、制作 JSON 或逐项核验。

业务执行前用 `bpm_login.py` 探查当前人员，以当次值绑定 `--expect-name`。模板制单人只用于核对指定样本，不能成为当前操作人。区分登录人、真实新页制单人/申请人、费用所属人及收款人；任意角色不明、同名不唯一或代办依据不足时记录具体缺口，不换人凑金额。

定向读取本次真实模板及唯一单号/UUID，核实表单和费用类别。再检查公里表结构、票据种类、用户意图及冲突；仅有“交通费”或历史备注不足以选择本手册。未知或多候选保持只读，其他已支持类型回统一入口，不硬塞进自驾。

当前缺完整装配时，可交付材料归集和有来源的核算结果，清楚写明没有实际填写；不能以“执行就绪”冒充用户要求的填写终点。

## 材料与来源

- 原件只读并登记哈希；整理副本平铺、防重名，保留原路径→原哈希→唯一票据→副本及哈希的可逆映射。随机数字名不是业务依据。
- 文件是容器，逐页/区域登记各票 `record_id`，多票不得只取首条；同票不同扫描去重，同金额不同票保留。单票提取器的多身份拒绝保护不放宽。
- 文本 PDF 优先机读，金额/票号通过原图视觉、已有汇总资料等适用独立通道复核；有汇总单时按票号逐项互证。扫描页视觉读取并留定位。汇总单不能再次计费，冲突不静默取舍。
- 无文本层时按既有逐页渲染/视觉复核路径处理，关键字段须有独立复核记录；仅完成一次读取或缺可靠复核依据时标待核，不生成可执行事实。并非所有票种都有汇总单，不因缺汇总单一项就强求用户补造材料。纯离线整理不要求模板单号/操作人，也不触发登录；本库返回缺口不能当扫描件已识别通过。
- 归集 API：`collect_materials(materials_dir, out_dir, write_copies=True)` 返回映射，`cross_check_summaries(manifest)` 返回互证结果，`analyze_pdf(path)` 提供逐页分析。由 agent 保留返回值、缺口和输出哈希；不要虚构不存在的 CLI 旗标。
- 若副本方向标签仅来自原文件名，它只供整理导航，必须由票面通行信息、公里表及公出事实核实后才可成为行程依据。开票日、实际通行日、目录名分别记录，不能互相替代。

## 工作簿与公出事实

识别实际 sheet、合并日期、去返行、用户公里数、通行费列及公式。只在同结构副本回填每张唯一通行票的准确行程，逐票恰好一次；同一行多票求和，未知/缺票/跨日歧义不平均分摊或填零。可靠重算后重新打开，逐行 Decimal 复算并保留单元格变更清单。原表没有餐补栏时，不擅改结构，餐补另列核算。

真实公出匹配须进入公出单模块，读取分页和全部相关事实行，按费用所属人的实际参与、事实日期/时段、路线及事由核对。人员与日期必须在同一事实行共同成立；不能用一行的人名和另一行的日期拼成参与证据，不按公出单制单人过滤同行人。

一单可多日、多票，同日可多事实。每张通行票都要有唯一最终结论并对应公里表行。填写前先落盘统计 MD 和机器记录：票号/源页/金额、行程和人员角色、Excel 行、完整公出单号、匹配依据、候选排除及占用状态、详情证据。未匹配或冲突继续阻断写入；不要求用户现场签字。

## 规则、餐补与覆盖

权威定义在仓库 `automation/business-scenarios/self_drive.json`；使用场景 ID、版本及文件哈希绑定事实/计划。调用 `evaluate_self_drive(verified_inputs, rules=load_self_drive_rules())`，不得省略 `rules=`；用 `rules_sha256()` 绑定配置。纯计算输入不能代替原件和参与事实验证。

当前规则口径：公里补贴按原公里数×配置公里单价；通行费按范围内唯一票金额；餐补按配置日标准，仅计本次真实制单人在本次范围内已核实参与的公出日，交集后按日去重。同日多单只计一次，不乘同行人数，不按票数或半日小时折算。没有参与依据不能默认零餐补或沿用模板人数、日期、金额。

`M` 为公里补贴，`T` 为唯一通行费，`C` 为有效日餐补，最终 `R=M+T+C`。油票仅组成覆盖池 `O`，`F=O+T`；必须严格 `F>R`，相等或不足均拒绝。油票不加报，汇总单不重复计费。

交通中的公里政策部分、实际通行票部分、餐补政策部分分开建模：通行票绑定实际费用组成，油票绑定覆盖池。不得把混合交通行全部伪称免票，也不删除其他类型的全票面分配校验。旧无餐补模型并存但不静默升级。

写入前须由绑定原始输入独立重算，核对逐行/逐日/逐单归属、票据与有效日唯一集合，以及 `R` 与计划主金额、报销明细、费用说明、银行合计一致；不能只验 coverage 声明块内部算术。目前此新模型到正式计划的绑定未接通，所以不得先填后补证。

## 关联、执行与保存边界

正常业务关联实际对应且合法可用的公出单；只有绑定具体材料、授权来源、任务和 `fill_only` 的受限历史测试才可使用真实可选占位。真实逐票匹配/应报分配与 OA 测试关联分开保存、核验及报告，不能互相冒充。必须核对真实枚举证据和哈希，不把字段格式或索引声明当内容已经验证。

正式接线完成后，仍复用 `fill_once.py`、`bpm/ui.py` 的单 profile 执行和独立终局 DOM 全量核验；不逐格运行旧脚本，不直接写接口。所有计划值、身份、行数、金额以及额外/重复/缺失数据都要检查。已有 FORM/SAVE 意图或未保存页按 registry 恢复规则处理，不换任务重建。

日常真实任务按用户策略在完整核验后自动保存草稿，具体授权和保护见 [入口保存策略](../SKILL.md#日常保存策略)。明确只填及受限占位不得保存；严禁流转、提交、保存并提交、上传、贴票和未知弹框自动确认。不能以“已有 Skill”替代同任务授权绑定或保存后持久化证明。
