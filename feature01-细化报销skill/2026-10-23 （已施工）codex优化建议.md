## 3. 实施范围与保留项

允许后续轮次围绕两个热点完善观测、区分控件场景、跳过已确认无效的操作、调整必要的预算依赖、补充局部验证与分析工具。允许增量修改主探针、相关离线验证及 docs/、automation/ 下必要工件；A 必须在每轮任务中具体列出改动范围。

所有轮次必须遵守：

1. **只填不存**。不得点击或通过接口执行保存、发送、流转、提交、上传、暂存、贴票、审批等动作；不得绕过或削弱 no_save_guard。本次修订不增加这些授权。
2. 保留 600ms 防御性轮询、Tab 失焦及三次回读等既有稳定机制，保留全局默认超时。本任务不做全面缩短等待或状态驱动等待替换；如需改这些保护项，作为后续独立任务另行明确。
3. 针对已确认消失的控件增加存在性判断、区分自动关闭与确认式弹窗，或为目标诊断调用设置局部超时，必须同时验证业务后置条件；不得以 force/JS 点击代替必要校验。
4. 经规则和页面证据确认的预算回显字段可以跳过通用写入，仍须由既有预算联动带出并最终核验。不能仅凭“当前没有 input”判断只读；编辑态延迟挂载的合法控件必须继续支持。
5. 选择器不得选表头；保留适用场景的 prescan、数据行身份、选中态及确认留痕。自动关闭的单据类型浮层与需确认的 p-dialog 应按各自机制核验，不能统一默认为选择成功。
6. 不静默改账号、金额、日期、关联单据或预算目标；不放宽业务匹配规则来制造通过。关联公出单替代仍保留既有授权记录和人工眼审事项；不在本任务内自动确认替代业务正确性。
7. automation/.pw-profile/ 内登录凭证不得进入 git、日志或报告；legacy-ia2/ 只读。保留其他 session 的既有改动，不将其误归为本轮改动或回滚。
8. 继续使用现有单执行者/profile 锁、--no-proxy-server 和 Windows 判活约束；Python 使用 -X utf8。浏览器被占用时记录资源阻断，不重复启动采集、不删活锁、不强关未保存表单。
9. 运行日志追加、新 attempt 独立留证；不得修写历史事件或旧结果来配合报告。实际生产异常记录需脱敏，避免输出凭证和完整敏感请求。

## 4. 全局 done_when：A 逐项验收

### D1. 操作边界与业务正确性保持

- 第 3 节约束全部成立。
- 本次计划中可填写、可核验项均回读一致，既有 29 项成功不得退化；结构性留空如实单列，不用推测填值补分。
- 改动保留账号、目标单据、预算和银行字段的身份校验；没有保存或提交流程证据不能声称已落库。

证据：代码差异、实际运行事件、fill_readback.json、stage1_result.json 和终局截图。

### D2. 观测能识别被内部捕获的异常及重试

- 关键动作可关联到 attempt、区块、行、字段或选择器场景；具备动作身份、开始/结束时间或可复算结束时间、耗时、尝试序号及总尝试次数。
- 两个热点中的实际控件读取/填写调用单独观测。在原有 except 吞掉异常或继续重试之前记录脱敏异常类型、耗时和继续/重试行为；异常仍按原流程处理。
- 区分“函数正常返回”“业务结果成功”“内部捕获过异常”。外层 outcome=ok 不能覆盖内部超时；字段失败返回值也须进入业务结果。
- 覆盖正常成功、缺失元素、不可编辑元素、内部捕获后继续及再次尝试的离线验证。记录真实异常，不把所有约 45s 的耗时直接改标为 timeout。
- 父子动作关系或包含区间可判定，后续分析不能把嵌套耗时重复相加。

证据：观测代码、离线验证输出和包含目标路径的真实运行事件。已存在的粗粒度计时可复用；缺失字段与路径必须补齐，不能靠报告解释替代。

### D3. 分解与根因报告可复算、措辞符合证据强度

- 明确定义技术执行、填写、登录等待和人工审单驻留各自的起止点；秒级事件与毫秒计时精度分别说明。
- 以不重叠区间统计顶层耗时；子项归属于真实包含它的父段，余量明确列为未覆盖或其他开销。表格合计与总量差异仅可来自声明的取整和覆盖边界。
- 对两处热点分别列出已观测事实、真实异常或状态证据、仍属推断的解释。离线实验和跨轮波动不能代替生产现场取证。
- 提供可复算的分析命令或脚本；A 能从指定原始事件范围重算关键数值。
- diff 区分本轮埋点/优化、等价表达拆分和其他 session 的既有改动；相同回读结果不能单独证明所有行为零变化。

证据：修订后的耗时报告、分析命令/脚本及原始工件引用。

### D4. 两处已确认无效操作完成局部优化

- 单据类型选择后，使用适合该浮层的后置条件核验，不再对已确认消失的行等待全局默认超时；确认式弹表的选中与确认验证仍有效。
- 已确认由预算联动带出的不可编辑预算字段不再进入重复填写超时路径；实际值仍经预算选择、带出和严格回读验证。
- 两处优化均有前置判据、成功后置条件和失败停止/报告路径，不以默认成功、忽略不一致或改计时口径换取提速。
- 性能证明须定位到目标调用：缺失/不可编辑控件造成的约 45s 超时及重复无效写入不再发生。仅报告总时长变短不满足本项。

证据：局部改动、针对失败模式的验证、优化前后对应动作事件及业务回读。

### D5. 验证覆盖真实控件机制与整单结果

- 每次修改主探针后，先运行 python -X utf8 stage1_probe_selftest.py，全绿后才运行真实填写。
- 局部验证至少覆盖：点击后消失的单据类型浮层、需要选中和确认的表格弹窗、预算不可编辑回显字段，以及双击后才挂载的合法编辑器。
- 至少完成一轮覆盖两个目标场景的优化后真实填写，保留完整结果、回读和终局截图，满足 D1。
- 登录人工门或资源阻断如实留证并按现有规则处理；未取得真实优化后结果时，此项未完成，不以离线页面替代。
- 单轮通过不表述为所有模板、所有账号、长期无人值守均已验证。

证据：既有自测、必要局部验证及优化后独立 attempt 的工件。

### D6. 效率结果与限制说明清楚

- 按相同定义对照优化前后动作、填写阶段和技术执行耗时，列出登录、模板规模、网络/机器条件等已知差异。
- 给出两处热点实际减少的无效尝试/等待、真实单据结果，以及仍存瓶颈。238s 与 330s 均为历史单次观测，不选择性引用有利数字。
- 2～3 分钟（120～180s）是实验目标，不是无条件承诺。未达到时报告实际效果和原因；不得为达数值删减复核、忽略失败或扩大范围。
- 不把人工审单驻留时间计入机器填写耗时；不把“函数返回正常”当作“无错误/无返工”。
- 整体提速幅度存在环境波动时明确说明；D4 的目标无效路径仍必须消除，不能用“波动”解释其继续存在。

证据：优化前后对照表及统一口径的原始计时。

## 5. 建议推进顺序

以下是里程碑建议，A 可在第 3 节边界内依新证据调整顺序和轮次划分：

1. **闭合观测**：验收当前 B 第 1 轮，修正报告错误并补齐 D2 的内部异常、尝试次数与对应现场证据。
2. **逐处优化**：先验证一个目标控件的正确交互，再处理另一个热点；复用已验证动作，不因一个字段失败重新探索整张表单。
3. **整单对照**：取得优化后真实结果，统一时间口径，复算改善并完成全局交接。

同一活页局部重试前先核对现场，避免重复加行或改错单据。只填不存时，磁盘进度不能恢复浏览器重启后已丢失的未保存数据；通用跨重启恢复不在本次验收范围内。
