# 指定模板和原始资料驱动报销完整开发任务书

日期：2026-10-24。适用仓库：`D:\Downloads\Mc Claude Code Workshop\2026-Auto-Pilot 企业微信`。

本任务书定义完整交付目标、开发范围、持续推进机制及最终验收条件，供多个 agent 跨 session、多轮执行。阶段划分用于安排工作；完成某个阶段、通过一轮测试或写出下一步建议，都不等于完成整个任务。

**最终用户只需指定一张完整单号的模板，提供本次原始资料和业务要求。agent 负责读取模板、理解 PDF/图片/Excel 等资料、核对事实、形成有来源的填写计划、完成真实网页新单填写，并自行完成完整独立回读及验收，交付填写结果和证据。用户不需要手工制作 task JSON、OCR 复核 JSON、字段映射或 fill-plan，也不承担施工过程中的人工核验。**

本次交付为任务书。实际开发、真实浏览器测试、材料核对和验收全部由后续 agent 持续多轮执行，不能把用户到场、手工核验、手工保存或人工签字设为完成条件。

**验收范围按用户最新要求修订：不测试保存按钮，不验收单据是否成功保存；唯一新单号/UUID、保存后重开、持久化及保存后只读恢复均不属于本轮必过项。其余原始资料、来源、金额、真实选择器、联动、全行填写、独立 DOM 回读及新 session 使用验收照常执行，由 agent 自行判断并留证。真实填写验收统一使用 fill_only，不因没有保存授权阻塞本任务。**

继承根 AGENTS.md 的全部红线。现有受控保存能力及其运行时保护保留；未来某笔日常业务另有明确保存指令时按原规则执行。本轮免验收保存成功，不等于可以降低保存守卫或把未保存状态报告为已保存。此前计划、报告中的保存待验事实保持原样，不能继续作为本任务的完成障碍。

## 1 最终工作方式

### 1.1 用户输入和预期结果

典型指令如下：

```text
请查看编号【完整单号】的报销单，以它为模板。
本次原始材料在【绝对路径】，包括发票 PDF、费用明细 Excel 等。
本次报销说明是【业务说明或应报范围】。
人员按当前已确认的系统默认资料，预算和收款资料按模板中适用于本次的资料处理。
请新建一张报销单，完成填写和完整独立核对，只填不存、不提交，给我填写结果和核验证据。
```

用户也可以明确指定申请人、收款对象、预算或关联单据。当前施工和验收以 `fill_only` 为准，无需用户参与中间步骤或对结果做人工核验。未来日常任务明确要求保存时，记录同 task_id 授权后走现有专用路径，不在每个内部步骤反复索取相同许可；该可选能力不扩大本轮验收范围。

正常完成后向用户返回：类别、模板号、本次总额、实际页面与填写状态、完整独立核验结论，以及 run/attempt、终局截图和证据路径。新页没有正式单号时如实报告未保存，不要求产生新单号。存在缺项时，agent 先从当前材料、已确认上下文或受控系统读取解决；确实缺少的业务事实记录具体位置和影响范围，不把用户人工验收作为处理办法。

### 1.2 合格的日常体验

- 用户提供的是原始资料。agent 完成内部材料清单、提取、分类、复核和计划生成，不能把编写 JSON 的工作退给用户。
- 读取用户准确指定的模板，不自动换成相近历史单，不为找一张单重做历史普查。
- 有效输入齐备时，从自然语言请求连续推进到用户指定的终点；不在“准备完成，请自行生成计划”处结束。
- 对已支持的正常场景走维护中的入口和共享代码。填写过程中无需 agent 逐格派发命令、临时 monkey patch 或修改 run 内驱动才能成功。
- 当前已确认的操作人和默认身份可继续使用，实际页面仍独立核验；不能把某次姓名永久硬编码进所有新任务，也不能按模板历史申请人自动换人。
- 不确定性集中处理。金额冲突、发票关键信息模糊、唯一选项不存在或必要物品档案缺失时停止依赖它们的写入，不能以猜测换取表面完成。
- 施工和验收由 agent 自主完成。独立复核可以交给另一 agent 或确定性校验程序，不要求用户现场对照、点击确认、手工保存或签收验收结论。

此目标允许 agent 使用模型理解非标准表格和图像，确定性计算和页面执行由程序承担。不要求制造一个能够无条件理解任何文件的一键黑盒 CLI；要求完整能力可由新的执行 session 按 skill 稳定调用。

## 2 本轮范围和结束边界

|---|---|---:|---|
| 第一批 | 差旅费 | 63 | 将当前材料理解、关联、费用、预算和银行填写串成原始资料驱动的正式路径，完成 agent 独立真实填写验收 |
| 第一批 | 快递费 | 23 | 复用现有执行能力，完成真实发票/结算 Excel 对账、新业务填写及独立核验 |

| 第二批 | 低值易耗品、办公用品采购 | 10 | 定向研究并接入实际普通报销场景，复用材料采购能力但不假定与研发物品档案相同 |
| 第二批 | 福利费、劳保用品 | 10 | 定向确认费用和必要名单/用途等材料，建模实际报销场景及相应核验 |

| 第三批 | 维修费 | 2 | 基于实际维修材料、预算、收款和关联结构接入 |

每类须有明确的支持场景和边界。类别名相同不代表所有业务分支都已支持；最终验收覆盖已承诺的常用结构、当前待办真实业务及本任务中确认必须实现的分支，未见过的任意异常形态不作无限承诺。

### 2.2 必须包含与暂不扩大项

必须包含：原始资料解析与复核、模板差异决策、来源绑定、金额与票据核对、计划生成、真实网页填写、agent 完整独立回读与复核、页面及证据交接、自动结果交付，以及八类按实证接入。保存按钮测试、保存成功证明及其依赖的重开持久化不在本轮验收范围内。

本任务不把公出申请、采购申请、合同、付款申请等独立单据的新建流程纳入交付；它们可作为确有依据的关联对象研究，操作能力不足则明确建模或报缺口。附件上传、贴票、提交、发送、流转、审批和直接写接口继续禁止。

部分票面报销、借款抵扣、数量乘单价等当前未支持的复杂分支，不能随新增类别自动放开。执行者发现其属于本次真实待办或样本中的必要主流程时，应登记为明确子任务，补齐契约、来源、计算、页面与验收后接入；在此之前拒绝受影响业务。超出本任务边界的业务不得改名、删行或改金额后伪装成支持场景。

### 2.3 完整任务的完成定义

只有以下条件同时成立，才可以宣布本任务完成：

1. 新 session 能仅凭本任务书、当前 skill、用户模板号和原始资料完成已支持业务；不依赖原作者私有聊天、历史临时脚本或用户手工填 JSON。
2. 八类都有具体支持范围、来源明确的规则/配置，以及与实际代码一致的能力状态；已承诺的场景完成必要实现。
3. 每类至少有一笔真实本次业务从原始资料到真实新页填写内容的端到端验收，通过本任务书第 10 节；相关重要分支有相应实测，不能用八张最简单单覆盖所有声明。
4. agent 自行完成全部字段、行数、身份、来源及金额的完整独立回读，并由独立 agent/校验过程复核证据；不以用户参与、手工核验或保存成功为条件。验收结束于内容真实填入且核验通过，报告实际未保存状态。
5. 所有相关离线检查通过，关键缺陷与反例闭合，最终代码/配置/证据哈希对应；正式入口无临时绕行依赖。
6. 用户看到的交付简洁准确，开发接力可从工件恢复，缺项和失败不会导致重复建单或误触保存；无人参与施工仍能完成已具备输入的验收。

若只能完成部分类型、材料链路或离线能力，交付对应成果并保留剩余目标；不能将本任务改写为较小范围后自行宣布全部完成。

## 4 模板和本次资料的职责划分

### 4.1 先固定准确模板身份

完整单号定向读取主表和全部相关子表，核对唯一 UUID、类别、数据完整性并保存快照和哈希。优先使用已完成的 `bpm_template.py`；缓存或 `--lookup-list` 只在其现有受控规则内使用，必须再次核对实时主表身份。保存后的新单重开仍按严格唯一身份定位，不能拿历史定位回退替代。

模板类别应从准确快照及当前映射识别。用户不用额外填写 document_type；若其业务要求与模板类别矛盾，集中报告，不悄悄换类或换模板。

### 4.2 建立逐字段复用决策

每个最终值须被归为稳定复用、当前事实、系统观察或明确计算之一，并留下依据：

| 内容 | 处理方式 |
|---|---|
| 表单类别、结构、字段和历史填写形态 | 模板用于识别结构与候选映射；当前页面仍重新验证 |
| 公司、流程归属、币种、预算及稳定收款资料 | 在本次适用并有依据时复用，不把模板旧年度和旧收款对象无条件沿用 |
| 当前默认申请人/制单人 | 根据本次用户政策及真实新页记录；不被模板历史人员覆盖 |
| 日期、期间、业务说明、费用行、金额、发票身份 | 只能来自本次材料、真实当前系统记录或用户明确业务事实 |
| 关联编号、物品档案编号、收款对象 | 必须证明属于本次业务，并在系统准确唯一命中；历史出现过不代表本次可用 |
| 合计或经允许的推导 | 使用明确公式和来源，用 Decimal 复算；不生成没有依据的业务事实 |
| 空表与不适用字段 | 由本次业务材料和已确认规则解释，不能因为模板为空就自动为空 |

产生可审查的“模板字段 → 采用/替换/不适用 → 本次值来源”结果。它可供内部复核和问题定位，正常用户不必逐字段审批。更换预算、收款对象或关联单涉及业务选择而当前证据不足时，才集中询问必要问题。

## 5 原始资料到业务事实

### 5.1 原件清单和派生材料分开

原始资料只读，不移动、不改内容、不把生成的复核 JSON 塞回用户资料目录。按内容哈希盘点文件，区分原件、重复副本、统计表、发票、结算凭据、说明及其他相关材料；文件名不能单独证明文件类别或发票身份。

当前 manifest 要求单一 root，且复核 JSON 与原件处于同一受控清单。本任务应解决“原件只读目录”和“agent 工作输出目录”之间的实际矛盾。采用明确的版本化契约管理原件根与派生根，或提供具有等价约束的实现；保留角色、来源关系、原件哈希、派生哈希和合法根边界，不能直接接受任意目录文件来省事。

旧契约保持可读及拒绝漂移的语义；新根/新版本不能自动迁移正在填写或保存中的任务。渲染页、OCR 结果、复核事实与运行证据进入本任务工作目录，避免被下一次材料盘点误当新的原件。

### 5.2 PDF 和图片

按当前环境可用的本地文档/视觉能力处理：可提取文本的 PDF 先保留文本及版面定位；扫描件或图片使用本地渲染和视觉/OCR 后复核。实际处理 PDF、图片和表格时使用环境适用的相关技能，不强行指定尚未安装的工具。不得上传未获授权的第三方 OCR 服务。

输出逐页/逐区域事实，至少覆盖相关票据身份、日期、开票主体、价税合计，以及本次费用行所需的项目、明细和金额。明确区分税前金额、税额与应付总额；折扣、退款、红字、模糊字符和多张发票共页不能靠猜测处理。

`reviewed=true` 只表示有实际执行的复核过程，记录 agent/工具/时间及复核方式，不能冒充人工审阅，也不能把 OCR 输出直接标为已复核。关键值至少回到原页检查；跨材料重复出现时再做一致性核对。模型置信度不能代替票号、账号、金额的准确性证据。

关键值不清晰时形成定位明确的缺口：文件、页码、区域、候选值或不确定原因、受影响费用行。清晰文件继续处理，不要求用户把整批资料重新手工录入。

### 5.3 Excel 和 CSV

识别工作表、表头、正文、合计、小计、备注、隐藏数据和重复统计范围。保留 `工作表!单元格` 或 CSV 行列定位，不默认第一张表或第一列就是费用明细。

金额、日期、数量、发票号、运单号、账号与业务编号分别解释。前导零和长编号保持字符串；原文件已丢精度的编号不能靠补零修复。公式单元格需可靠的已算结果或经过验证的本地重算及公式复核，不能拿公式文本当金额，也不能不查缓存时效就相信旧值。

不能按“每个非空行生成一条报销费用”的规则机械转换。特别检查统计合计与明细是否属于同一费用，跨 sheet、跨文件是否重复，筛选/隐藏行是否在本次范围内。数量相同、金额相同并不等于重复业务。

### 5.4 建立本次业务事实和缺口清单

把原件解析结果组织成版本化的内部业务事实层，具体名称可随实现确定。至少能表达：本次业务身份/范围、费用事实、票据事实、预算/收款候选、必要关联/档案、适用性理由、来源定位、推导和未决问题。

来源必须区分原件、准确模板、用户明确指令、当前系统观察及确定性计算。不能为了让现有 `kind=user` 校验通过，把 agent 自己的推断改写成“用户已确认”。需要新来源种类时同步更新 schema、解析器、核验与拒绝反例。

每条事实有稳定 ID。后续计划行和发票分配引用这些事实；材料换版本后识别受影响事实，重新规划与校验，不修改已执行计划来掩盖来源漂移。

## 6 对账和计划生成

### 6.1 对账必须先于业务写入

至少核对：

- 同一发票的不同扫描件、同一文件多张票、重复费用统计、汇总与明细重复计入。
- 每张票面金额与其分配金额闭合；每个主要费用行有完整发票分配或有本次来源支持的免票依据。
- Excel 与发票、结算明细与合计、本次说明与费用范围一致；冲突不得任选一份当真。
- 报销总额、明细合计、收款合计，以及各类适用的费用说明或档案金额分别闭合；不同层不能相加重复计费。
- 收款人、账号、支行及联行号的完整身份；系统实际选项与本次依据一致。
- 未经建模的借款、部分报销、未知业务表及金额语义不得进入保存路径。

分类、去重与对账需要区分“明确重复原件”和“金额相同但确实不同的业务”。同一金额不构成全局禁报规则；同一发票跨任务可能重复使用时应提示已有意图及历史证据，不通过新 task_id 绕过。

### 6.2 agent 负责生成可执行计划

由业务事实和本类规则生成 fill-plan，agent 处理有依据的语义映射，程序处理结构、来源和 Decimal 校验。所有执行值、空表理由、授权、模板、原件和派生材料都有准确来源与哈希。

归并或拆分费用行必须有本次材料和实际 OA 结构依据；归并后保留原明细到计划行的映射。不得为了减少页面操作，把必须分预算、分收款人或逐档案填写的数据强行合并。

计划完成后自动调用现有完整离线验证；失败时先修正内部提取/映射错误，真正缺业务信息才反馈用户。内部“解析完成但尚待 agent 生成计划”不能作为最终 NEEDS_INPUT 回答；可以增加与业务缺口不同的内部阶段状态，且不得把中间状态包装成成功。

### 6.3 版本和输入绑定

模板、原件、派生事实、规则配置、计划、操作人及执行源码建立可追溯绑定。执行前、阶段边界和保存前按现有要求检查漂移。缓存以内容哈希为键，不能替代最后的新鲜 DOM 回读。

有兼容变更时保留旧版读取与核验路径，禁止修改原 run、旧 manifest 或 registry。准备期修订采用明确版本；已开始业务写入后计划不能原地换值，按当前恢复规则处理并说明页面已有内容。

## 7 正式网页执行和安全恢复

本轮正式路径为：请求登记 → 定向读模板 → 原件解析与复核 → 本次事实与对账 → 计划生成和验证 → 新页预检 → 连续填写 → 完整独立回读 → agent 独立复核 → 填写结果与证据交付。施工过程不等待用户到场、人工对照或保存。

复用 `fill_once.py`、`bpm_ui.py`、`bpm_verify.py`、`bpm_save.py`；可以增设明确的准备/规划模块或上层入口，但不能以另一套无守卫脚本绕过现有执行器。skill 中说明阶段如何衔接，保持当前低层 CLI 兼容，不暗中把原 `--task` 的离线语义改成自动写生产。

真实类别、预算、科目、银行、关联、人员和档案全部唯一准确匹配。默认银行行、只读汇总、物品档案带出等采用已有严格分支和证据，不扩大为通用默认放行。

本轮真实浏览器验收使用 fill_only，不测试保存按钮，不为验收创建已保存单据，不要求新单号、重开或持久化证明。现有保存控制器和相关离线保护保持兼容。若未来具体日常任务另行调用保存能力，仍按 AGENTS.md 的完整安全条件执行；免验收不意味着免除该运行时规则。

遇到保存结果不明确，保留 SAVE_UNCERTAIN，转只读核实；已有 SAVE_INTENT、SAVE_UNCERTAIN 或成功记录不得再保存或另建。保存后的同任务恢复也必须只读定位原单。

未保存页当前只能盘点交接。若实际日常任务确需安全恢复当前活页，可以登记独立子任务，在页面身份、原计划/源码/配置绑定、新鲜完整回读、唯一写入者与幂等范围有证据后实现；跨重启恢复不能顺带宣称支持。没有可靠恢复条件时保留原页、状态和工件，记录 agent 后续可执行的处置或准确外部缺口，不能清 registry、换任务重建或把用户到场处理设为正常验收步骤。

保留 600ms 轮询、Tab 失焦、重复回读、Windows 判活、profile 锁和 OA 直连要求。性能继续通过减少重复解析、重复映射和临时模型往返改善，不删核验、不压防御等待。

## 8 类别扩展和必要业务分支

### 8.1 现有三类先形成完整闭环

差旅按本次行程、费用、发票及实际关联组织多表计划，不从旧单推导本次关联、餐补资格或天数。公出/出差等当前已支持分支按现有严格规则处理，未建模分摊仍拒绝。

快递把运单/结算/发票与 Excel 统计对应到主要费用行，覆盖费用说明有/无、多行和多票场景。历史回放 8 行和 4 收款只是页面能力证据，不能替代新原件对账。

研发按本次实际业务给出的档案编号准确选入现有档案，核对名称、购买人、价格和备注。原件有数量单价不代表 OA price 就是单价；依据已确认行额语义处理。需要新增档案而当前无能力时报告明确缺口，不用历史档案代替本次物品，不伪造只读字段。

### 8.2 其余五类按准确模板接入

盘点已经提供候选完整单号，只作为定向研究入口，不作为新业务事实或保存授权：

| 类别 | 研究候选完整单号 | 需要确认的差异 |
|---|---|---|
| 低值易耗品、办公用品采购 | 15426101596、15426093534、15426070765 | 实际物品/采购明细、是否使用档案、预算和付款对象 |
| 福利费、劳保用品 | 15426071883、15426052980、15426031965 | 本次用途、必要人员/发放资料、费用项目与收款结构 |
| 其他费用 | 15425125587、15425052077、15424124912 | 各样本业务含义与差异；只注册已明确的具体子场景 |
| 维修费 | 15426015123、15425042138 | 维修对象、服务明细、结算/发票和必要关联 |
| 各项会议支出 | 15425044882 | 会议业务范围、必要明细材料、费用项目及金额口径 |

每类循环：完整主/子表和真实页面观察 → 业务材料与规则确认 → 差异说明 → 封闭注册/配置/schema/参考 → 必要共享能力 → 离线测试 → 授权范围内真实控件测试 → 真实本次业务端到端验收 → 能力状态和交接更新。

内部类型标识、API 代码、字段与选择器必须从实际证据确定，不能从中文名称猜测；新增 JSON 文件本身不自动启用类型。同流程且只是字段/材料差异时沿用现有 skill；真实流程独立时再定义明确业务分支，避免每个按钮一个 skill。

### 8.3 未知模板的日常行为

未知或未登记类别：先定向只读识别，输出具体不支持部分及已有证据；可整理材料，但不执行未知表单写入。登记开发子任务，沿上述接入流程完成后再启用。日常任务不能现场无限打补丁、自行放宽守卫或临时映射到“其他费用”。

## 9 工作包和持续多轮推进

### 9.1 工作包及验收出口

| 编号 | 工作包 | 必须交付 | 验收出口 |
|---|---|---|---|
| W00 | 接手基线与总台账 | 最新源码/能力/证据、未完目标、输入与授权清单 | 旧成果已复用，差距有准确依据 |
| W01 | 用户请求与模板决策 | 请求记录、唯一模板、类别识别、复用/替换矩阵 | 用户不用填写内部契约，错模板不被执行 |
| W02 | 原始资料工作区 | 原件盘点、派生目录、版本化来源与路径约束 | 不写原件、可定位、不可越界或漂移 |
| W03 | PDF/图片/表格理解 | 提取及真实复核、单元格/页区域证据、结构化缺口 | 清晰原件可由 agent 自行处理，模糊关键值被拦截 |
| W04 | 本次事实与对账 | 票据身份、费用范围、归并映射、金额/多来源核验 | 重复、冲突和未覆盖行在写入前阻断 |
| W05 | 计划生成与衔接 | 可执行计划、schema/业务验证、阶段串联、状态区分 | 不再正常停在“请用户提供 fill-plan” |
| W06 | 三类端到端成熟化 | travel/express/rd_materials 正式路径及必要修复 | 三类分别通过第 10 节验收 |
| W07 | 两类中频接入 | 低值办公、福利劳保的配置、规则、实现、证据 | 两类分别通过同等验收 |
| W08 | 三类低频接入 | 其他、维修、会议的明确支持子场景及证据 | 三类分别通过同等验收 |
| W09 | 无人参与的独立验收与交付 | agent 独立复核、完整 DOM 证据、实际页状态与结果报告、安全页面交接 | 无需用户人工核验；内容通过且未误触保存/提交 |
| W10 | 新 session 验收与最终交接 | 独立使用结果、最终清单、资料与入口更新 | 全局完成定义逐项满足 |

W02 至 W05 是下一轮应优先完成的主线，不能只接入更多类别就跳过。材料/计划模块与只读类别研究可以并行；共享文件修改和浏览器操作按所有权与 profile 独占串行集成。W09 伴随每类执行，独立 agent 按原始证据验收，不交给用户手工核验，也不等待保存成功。

### 9.2 多 agent 分工

按执行环境实际可用的 agent 数量安排，不为凑角色建立新协作平台。建议职责如下：

- 协调/集成 agent：持有总目标和台账，管理文件所有权、版本冻结、任务分配、输入/授权缺口，组织正式端到端执行并判断整体状态。
- 材料与规划 agent：负责原件工作区、提取复核、本次事实、对账和计划生成，提供有源数据及有效反例。
- 类型与网页 agent：负责分配到的类型配置/规则/页面适配；共享注册与核验文件先交由明确所有者集成。
- 独立验收 agent：基于原始输入、实际代码和原始证据检查结果，复算金额与覆盖，承担本轮最终内容验收；不能仅复述实现者的成功摘要，也不能要求用户代为验收。

分派时明确文件/模块所有权和交付物，说明存在其他开发者，不回退他人改动。一个共享文件同一时段由一名集成者修改；子 agent 可提交修改建议或补丁。只有登记的唯一网页执行者使用 profile，其他 agent 只读工件或做离线工作。

### 9.3 每轮必须完成的闭环

每轮按以下步骤推进，不把“生成下一轮计划”当唯一产出：

1. 读取总目标、最新台账、上轮交接和相关原始证据，确认源码/配置是否漂移。
2. 选择最靠近最终闭环、当前可完成的工作包或未关闭缺陷，明确本轮交付和影响范围。
3. 实现并验证；真实控件失败先定位机制，再修复共享实现，增加相应反例，按需复测。
4. 将结果绑定实际源码、配置、任务/材料及证据，独立核对；不能仅凭退出码或实现者摘要打通过。
5. 更新唯一进度台账、未关闭问题和接力入口。仍有可推进任务时进入下一轮；只有总体完成或确实依赖外部输入/登录/资源时，才交代明确等待条件。

相同错误无新证据时停止盲重试，先做原因分析；没有新输入的外部等待不反复执行同一网页动作。不因单轮时间或上下文结束将总任务标完成。

## 10 测试体系与真实网页强制验收

### 10.1 三层证据不能互相代替

| 层次 | 目的 | 能证明什么 |
|---|---|---|
| 原件与离线行为测试 | 验证提取、事实、来源、金额、计划及异常阻断 | 数据处理和程序规则正确，不证明真实 OA 控件可用 |
| 真实网页授权测试/历史回放 | 验证准确选择器、联动、复杂行和回读 | 对应网页动作可执行，不证明新的费用事实或新业务保存 |
| 本次真实业务端到端 | 从用户原始 PDF/Excel 生成并执行计划，真实填写、agent 独立核验和交付 | 原始资料到真实内容填写的最终工作方式在已列业务范围内成立 |

三类已有的真实历史回放继续作为第二层证据使用，不要求重复获取同样结果；第三层必须补齐。

### 10.2 原始材料和异常测试矩阵

至少覆盖以下有实际意义的行为，不机械追求固定测试数：

| 测试点 | 期望行为 |
|---|---|
| 文本 PDF、扫描 PDF、图片，多页或一页多票 | 提取与页/区域准确关联，票据数量与实际一致 |
| Excel 多 sheet、公式、汇总/明细、隐藏或筛选数据 | 按本次业务范围解释，不重复合计；公式结果可靠 |
| 前导零、长票号/账号、模糊关键字符 | 原值保留；丢精度或模糊时阻断受影响行 |
| 相同文件副本、不同扫描同票、相同金额不同业务 | 分层去重，不漏报、不重复报 |
| 票面与 Excel 冲突、含税/未税混淆、未覆盖主要费用行 | 写入前拒绝并准确定位原因 |
| 原件/提取/模板/配置变更、派生路径逃逸 | 旧计划失效或拒绝，不拿旧复核冒充新输入 |
| 模板人员不同、当前默认身份、供应商/员工收款差异 | 按本次身份政策执行，准确核对，不借历史姓名换人 |
| 多行、多票、多预算、物品档案、空表 | 全量来源与行数闭合，不只核对前两行或合计 |
| 类别不匹配、未知类型、未知表、未建模数量/借款 | 明确拒绝，不映射到其他类别绕过 |
| 保存不确定、重试、同任务恢复 | 最多一次保存，只读核实原任务，不建第二张 |

### 10.3 真实浏览器测试是必过关卡

**必须使用真实 Chromium/Playwright 访问实际 OA 网页开展测试。localhost、静态 HTML、DOM 夹具、接口回放及测试替身均属于离线或模拟证据，不能在本台账中标为真实浏览器验收通过。**

页面相关改动按“实现 → 相关离线检查 → 真实浏览器局部验证 → 正式入口整单验证 → 独立核对”推进。已经有适用且版本匹配的实测证据可以复用；影响选择、写入、联动或核验的改动必须补验对应真实步骤，不能只补一个本地测试就结束。仅材料解析等不影响页面机制的改动，验证其数据行为后仍需在最终端到端任务中检验衔接。

| 浏览器关卡 | 实际动作 | 必留证据 |
|---|---|---|
| B1 实际入口与身份 | 真实登录、准确模板查询、进入实际新单，核对当前身份和页面类型 | 页面/模板唯一身份、操作人证据、截图和源码/配置绑定 |
| B2 真实选择器 | 实际打开并操作类别、项目、预算、科目、银行及适用的关联/档案弹窗 | 查询、唯一命中、选择确认和最终显示值；不预填目标结果代替选择 |
| B3 动态联动 | 类别切换、增行、默认行带出、只读字段计算及 Tab 失焦 | 联动前后独立观察、准确列/行及最终稳定回显 |
| B4 正式整单执行 | 使用正式入口完成本类承诺场景的所有业务行 | events、全部行数、终局截图、无临时方法替换的执行版本 |
| B5 独立真实回读 | 从当前实际 DOM 重新读值并核对全部字段、额外数据及金额 | 新鲜快照、完整核验结果、差异为空的证据 |
| B6 agent 独立验收 | 另一 agent 或独立核验过程依据原件、计划和实际页面证据复核结果 | 字段/行/金额覆盖、原始证据引用和明确通过/失败结论，不依赖用户 |
| B7 页面状态和结果交付 | 记录真实填写页身份、未保存状态和页面处置，生成报告 | run/attempt、终局截图、完整内容核验结果、页面盘点，无保存/提交动作 |

不得通过浏览器 evaluate 直接修改表单业务值、伪造选中对象、改页面状态文字或拦截写响应冒充正常 UI 成功。evaluate 可用于独立读取和必要定位；真实写入使用已经建模的原生控件交互及守卫。

每类至少一次真实整单通过 B1 至 B7，全程由 agent 完成；B6、B7 不涉及保存按钮或持久化。新业务原件链路和全部内容核验通过时，可标为本轮端到端验收通过，不因未保存而阻断。历史回放仍只能证明其实际覆盖的内容和网页动作，不能冒充本次原件解析验收。

### 10.4 每类真实业务验收标准

每类至少一笔本次真实业务满足 A1 至 A9；常用复杂分支未被这笔覆盖时，按已承诺矩阵用后续真实业务补齐。不得为凑覆盖制造虚构费用或重复保存同一笔业务。

| 编号 | 必验项 | 必须看到的证据 |
|---|---|---|
| A1 | 只交模板号与原始资料即可开始 | 原始用户请求、模板唯一身份、资料清单；用户未被要求手写内部 JSON |
| A2 | agent 自行完成原件提取和复核 | PDF 页区域/Excel 单元格、原件与派生哈希、关键事实复核和缺口处理 |
| A3 | 模板复用与本次事实正确分离 | 稳定字段复用决策，日期/费用/票号/金额等本次来源，不偷用历史值 |
| A4 | 对账和计划有效 | 发票身份与分配、跨来源一致性、各层金额闭合、完整来源及正式验证结果 |
| A5 | 正式入口真实网页填写 | 真实身份、类别/项目/预算/银行/关联/档案选择、全部行及联动证据；无临时方法替换 |
| A6 | 完整独立回读 | 新鲜 DOM 对全部计划值、行数、额外/重复/缺失数据和金额复算，无差异 |
| A7 | agent 独立复核通过 | 依据原件、计划和真实 DOM 证据再次核对全部内容；无用户人工验收步骤 |
| A8 | 真实填写页状态明确 | 页面身份、实际未保存状态、全部内容与截图已留证；无保存或提交动作 |
| A9 | 自动交付与安全接力 | 正确类别/模板/金额、填写核验结论、run/attempt、截图和页面交接齐全；不等待用户手工保存或确认 |

fill_only 任务能够完成本轮 A1 至 A9 全部验收。A7 至 A9 是 agent 自主复核、页状态和交付要求，不是保存链路；不要求用户手工核验、手工保存或反馈成功，也不因未生成正式单号而失败。

### 10.5 测试授权和生产边界

沿用已有明确授权的真实网页研究和历史回放范围，不重复询问同范围许可；记录授权来源及适用类型、目的、模板和模式。此前两类 test_context 强制 fill_only，不能改旧计划把回放升级为可保存任务。

本轮所有真实填写测试均使用 fill_only，不需要保存授权，不要求用户配合测试保存按钮或回报保存结果。测试页证据、状态盘点和按既有授权允许的收尾由 agent 完成，不把“留给用户现场核验/保存”写成验收动作。正式业务页面按任务要求保留；本轮自建临时回放页按现有规则正常收尾，不关闭其他 session 页面。

错账号、错金额、网络故障、未知弹框、数据篡改和重复保存等反例在离线或适当隔离环境验证，不故意污染生产。失败返回真实状态：WAIT_HUMAN_LOGIN、NEEDS_INPUT、READBACK_MISMATCH 或 SAVE_UNCERTAIN，不能过滤 issues 或改名为成功。

### 10.6 新 session 独立使用验收

最后安排未参与对应实现的 agent，仅获得当前 skill、本任务书、完整模板号、本次原始材料和本次指令，按正式路径执行已登记且未执行过的真实任务。不得提供人工制作的最终 fill-plan 当作用户输入，也不预告要抄哪些历史值。

由唯一网页执行者串行运行；独立 agent 承担材料/计划和证据审查，内容验收不得转交用户。已经保存过的业务只能用作只读核实，不为新 session 验收重复新建。若独立使用仍需原作者临时补丁或解释私有约定，登记问题并修复后再验收。全部 A1 至 A9 由 agent 给出有证据的结论，无需用户现场参与。

## 12 总台账和交接工件

### 12.1 唯一进度来源

建议在执行时建立 `automation/template-materials-program/`，由协调 agent 维护最小总台账，例如 `progress.json`，并在本目录维护一份便于用户阅读的推进记录。任务目标和验收标准以本文件为准；动态状态只有一个权威来源，Markdown 是其可读摘要，不维护互相冲突的完成清单。

总台账至少记录：工作包/类型/场景 ID、状态、负责人、源码/配置版本、证据引用、未关闭缺陷、缺失输入、授权范围、正在占用的 run/profile、下一项可执行工作及全局剩余条件。不要复制凭证或把材料敏感值贴进协作消息。

工程阶段、真实任务和保存状态分别记录，不把“代码完成”写成 SUCCESS_DRAFT_SAVED。可以使用明确的工程状态：待做、进行中、待复核、缺外部输入、已验证；每个“已验证”都有对应层次和证据。

### 12.2 每轮交接内容

每轮结束记录：

1. 本轮完成了什么、解决了哪个具体缺陷、影响哪些工作包/场景。
2. 改动文件、最终源码/配置/契约哈希及实际检查结果，哪些旧结论因版本变化需要重验。
3. 真实任务 run/attempt、页面是否仍开、是否有保存意图、唯一单号/UUID、当前应当只读还是可以继续填写。
4. 证据路径和未关闭项，区分代码问题、业务缺口、授权、登录或资源占用。
5. 下一轮可直接执行的入口；原总体目标还缺哪几项，不只写一句“继续优化”。

真实任务证据继续使用 `automation/runs/<run>/events.jsonl`、attempt 下的 `stage1_result.json` 和原证据目录；离线结果进入 `automation/offline-verify/<run>/`。总台账引用它们，不能另建一套“成功日志”取代权威结果。

### 12.3 最终交付清单

- 维护中的业务入口、解析/事实/对账/规划及正式执行代码，必要依赖和版本化契约。

不得自动 commit、合并或上传业务材料；用户已有具体版本管理授权时按其范围执行。

## 13 外部输入缺口与继续策略

构建代码、离线验证和已有范围内的只读/回放工作无需等待所有真实业务一次性到齐。agent 优先盘点已有原始材料、授权、完整模板和系统证据，自行选取在授权范围内可执行的验收任务；每类一笔起步，按实际场景补齐。施工和验收不安排用户参与，不将用户现场检查、反馈或保存作为测试依赖。

操作人已经在当前上下文及真实页面得到确认、用户要求保留默认时，不反复索取；需要新登录或身份变化时再准确核验。模板研究候选可以自行从既有列表按完整身份选取；正式业务执行仍使用用户明确指定的模板。

真正无法从现有资料和系统解决的缺口，如某类没有本次原件、关键值不清、必要档案/关联不可用、登录失效或 profile 占用，由 agent 记录准确原因和受影响范围并继续独立工作。不得把缺少保存授权、没有用户人工核验或用户未手工保存列为本轮阻塞项。无法创造的业务事实和登录条件仍须如实记录，不能伪造、绕过守卫或宣称已验收；这属于外部条件缺口，不是要求用户执行验收步骤。

外部缺口长期未解除时保留任务未完成状态及清晰恢复条件；不能无限重复同一等待，也不能把“已经写出计划/框架/离线通过”作为总任务结束理由。
