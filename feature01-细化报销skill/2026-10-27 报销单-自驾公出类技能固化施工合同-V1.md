## 1. 最终目标与用户入口

用户以后只需提供：

1. 本次所有原始发票/票据及统计 Excel，可放在同一目录，也可分别指定路径；本轮自驾场景的 Excel 含用户公里数。
2. 明确的 OA 参考单据完整单号，例如“徐亮-报销单-15425123013”；姓名/标题用于定位并核对模板，不代表指定本次登录人或授权代办。
3. 一句执行意图，例如“按这个样本完成本次报销填写，暂不保存”。不要求用户预先判类型、编写内部 JSON、提供计划或逐项指导。

预期使用示例：

> 材料在 `本次材料目录`，参照徐亮的报销单 `15425123013`，完成本次报销填写，暂不保存。

agent 自主完成：

```text
请求登记与用途绑定 → 当前登录身份核验 → 指定模板真实只读读取
→ 核实真实表单种类/费用类别 → 结合本次材料识别业务场景并检查支持能力
→ 本轮匹配“报销单 / 差旅费 / 自驾公出” → 加载对应 runbook/规则
→ 原件分类、提取、去重、规范命名归集 → 公里表副本回填与可靠重算
→ 真实公出单逐行程/逐票匹配 → 先生成统计明细 MD
→ 从原件独立计算并逐行、逐日、逐单校验 → 生成、绑定并验证执行计划
→ 真实 OA 完整填写 → 独立 DOM 全量核验 → 交付文件、证据及未保存页面
```

这是统一用户入口，自驾公出是本轮落地的一个场景。后续新增场景或单据类型仍复用“给材料＋指定模板＋说明意图”的方式；各类型声明所需材料，不预设所有未来任务都必须有发票、公里表或公出单。接入边界见 §3.2。

对已支持且输入可核实的任务，`NEEDS_INPUT`、`PLAN_READY`、`EXECUTION_READY` 都是阶段状态，不能代替填写交付终点。真实身份认证、不可自行查证的业务事实冲突、未支持/无法确定的类型或运行时保护门可阻断相关写入，其余独立工作继续；本合同应实现的能力尚未完成不能包装成外部缺口。用户不承担业务施工、内部数据准备或内容验收签字。

## 3. 固化方式与职责

采用**一个既有入口 Skill＋一个自驾公出 runbook＋程序校验及回归用例**。不另起浏览器执行器、通用工作流平台或第三个常驻调度角色。

| 落点 | 职责 |
|---|---|
| `.claude/skills/bpm-fill-run/SKILL.md` | 统一入口、接单、模板读取、类型/场景路由及能力检查、阶段推进；按需加载对应手册，保留其他类型入口 |
| 新增 `references/self-drive.md`（位于同一 skill 内） | 自驾公出的材料、业务解释、来源、匹配、填写、异常及交付操作手册；不再维护一份与其重复的独立 skill |
| 版本化自驾规则配置 | 集中保存适用范围、公里/餐补单价、覆盖策略及用户规则来源；runbook 引用，程序读取，计划绑定版本和哈希 |

### 3.1 识别与路由

- 先从真实模板核实表单种类及费用类别，再识别业务场景。当前注册的 `document_type` 含义保持；本场景仍是 `travel / 差旅费 / 08` 下的“自驾公出”，不伪造系统不存在的新类别，也不把其他表单硬塞进 travel。
- 结合真实模板表结构/费用项目、本次公里统计表、油票/通行票及用户意图识别场景，输出采用证据和排除依据。不能仅凭单号、备注“公出油补”或“存在交通费”就把所有差旅判成自驾。
- 用户给出模板制单人时核对真实样本；完整单号与 UUID 唯一匹配。模板跨制单人、跨年份时，使用合法的精确查询/既有身份索引辅助并由新鲜主表互证，不为找一张单普查全部历史。
- 正常输入不要求用户再手选内部类型或补 JSON。确有歧义时集中报告具体冲突，不误路由继续写入。

### 3.2 有限扩展约定

- 保留一个入口 Skill，场景操作细节按需加载独立 runbook（即 `references/` 中的操作手册）；同一业务规则只保留一个权威定义，由手册解释、程序校验。无需每种场景再建一套入口技能。
- 沿用现有类型注册与配置，补最小的场景映射即可：适用的真实表单/类别、场景 ID 与版本、识别依据、所需材料、手册/规则位置、对应的已实现校验与执行能力。可为普通配置或显式代码表，不建设插件平台、动态代码加载或另一套调度系统。
- 路由结果记录模板证据、采用的类型/场景及规则版本；“能识别”“已有实现”“离线通过”“真实填写通过”分开报告。证据冲突、多候选或已识别但尚无执行能力时，只读整理缺口，不能默认为自驾、套用相近类别或声称已支持。
- 后续新增同一表单下的场景，补相应手册、规则、校验和验收；新增真实表单种类，再补所需读取/填写适配及安全验证。先检查可复用能力，不要求每次重写公共入口，也不允许只加文档就开放未知页面写入。
- 本轮只落地自驾公出及以上接入约定，验证既有类型不受影响和未知类型安全停止；其他新类型的生产实现与真实验收不列入 D01—D13 的完成门槛。

## 4. 业务合同

### 4.1 任意同事与 30 天登录管理

- 每次业务开工、扫码成功及账号切换后，按 profile 锁保护的真实认证和身份探查取得当前人员。尽量获取企业微信/OA 姓名、工号/用户 ID、公司和部门；未知记录 null 及原因。同名不能只凭姓名匹配。
- 扫码时及后续探查更新 repo 内 Git 排除的本机身份/会话记录；认证值仍只在受保护凭证目录。元数据、凭证都不进 Git、通用夹具、材料 manifest 或跨 agent 消息；实际使用前验证 `git check-ignore`。
- 新默认本地窗口为 `last_scan_at + 30 天`；有效边界取该上限与已知相关服务端期限的更早者。普通探查不重置扫码起点，不改 token/cookie 到期值。服务端提前撤销就停写并要求必要扫码，不能承诺必然免扫码 30 天。
- 旧记录保留可信扫码起点与历史事实。合法旧 60 天记录按 `min(原本地窗口, 30 天)` 收紧，不能仅改常量就把尚在新窗口内的旧记录一概拒绝、强迫重新扫码；已过新边界则失效，更短旧窗口不得被延长。读取判定、非扫码探查写回和显示期限使用同一口径，不改扫码起点或会话代次，不通过 mtime、补写“今天扫码”续期。无法验证的元数据仍拒绝；没有可信扫码时间的旧状态沿用既有保守边界，不凭文件时间补猜。
- 区分登录操作人、真实新页制单人、申请人、费用所属人和收款人。用户未另指定时使用本次验证身份及系统默认资料，再与本次材料核对；模板中的姓名/账号不自动成为本次身份。明确代办须有本次依据且走已有合法 UI，不强写制单人、登录后不偷换人。
- 本例实际费用归徐亮，不能因当前登录为另一同事就改按另一人的公出单查找。真实写入时身份关系必须合法成立；必要身份冲突是真缺口，不能为了复现样本金额绕过。其余解析、对账和只读查找继续。

### 4.2 票据识别、重命名与归集

- 随机数字文件名不携带可靠日期或行程。先读取内容，再按票种、实际日期、路线/方向、票号等规范命名，归集**整理副本**到一个文件夹；原始资料保留只读及哈希。
- 通行票使用实际通行信息；油票使用票面信息，不虚构对应行程。开票日期、行程日期、目录日期分开；汇总单区分“票据汇总”和“行程汇总”，不当成新增发票。
- 文件名应可读、确定且防重名，例如 `日期_票种_方向或路线_票号_短哈希.pdf`；缺失路线、重复扫描须有明确命名/分类规则，不为凑文件名猜字段或覆盖已有文件。
- 区分“原始文件”和“唯一票据”：多票 PDF/合并图片是容器，按页/区域定位其各票身份，建立一对多映射；文件可整件留副本，不要求用户拆原件。现有单票提取器检出多票后拒绝的保护保留，由归集层分件取证后调用，不能只取第一票或因原文件哈希相同而合并不同票。无法可靠分件/读值时列明页、区域和具体缺口；本批原件未处理完整不能判 D04 通过。
- 保留原路径/原名→原哈希→唯一票据身份→整理文件名/哈希的映射。不同扫描中的同票去重，相同金额的不同票不合并；同一输入重跑不增加重复计费或覆盖原件。
- PDF 文本层优先，图片/无文本层再视觉复核，关键票号/金额用独立渠道互证。所有 PDF/图片逐页分类，不能只处理文件列表中看起来像发票的一部分。

### 4.3 公里表副本回填

- 识别真实 sheet、合并日期、去返行、公里数、补贴、通行费及公式。保留用户公里数、原结构和无关格式，不能按票据路线反改公里数。
- 每张唯一通行票分配到准确行程/方向，逐票恰好一次；同一行多票求和。未知、缺票、跨日歧义不能平均分摊或填 0 隐藏。
- 在同结构副本回填通行费并可靠重算，重新打开核对逐行与合计；独立 Decimal 复算，不能只读旧缓存或比较公式文本。变更清单列 sheet/cell、原值/公式、新值/公式、票据来源。
- 原始公里表没有餐补栏时，不擅自改变其结构；交通副本仍表达公里补贴＋通行费，餐补另在计算/对账明细中列出，并明确交通小计与最终报销总额的区别。

### 4.4 金额、餐补及严格覆盖

金额统一人民币元与 Decimal，两位货币精度；标识符保留字符串及前导零。

```text
每行交通 = 原始公里数 × 1.00 + 该行唯一通行票金额之和
M = 全部公里补贴合计
T = 全部范围内唯一通行费合计
C = 本次报销单制单人在本次报销范围内、已核实参与的有效公出日去重数 × 30.00
R = M + T + C                         # 新规则最终应报额
O = 本次有效、去重的油票价税合计
F = O + T                             # 票据覆盖额，不是费用额
允许填写的金额条件：F > R             # 等于或小于均拒绝
```

- 餐补仅计本次报销单的真实制单人，须有其实际参与本次公出的依据；不是模板制单人，也不是每张公出单的制单人。每个有效公出日一次 30 元，不乘同行人数、不按票数或关联单数计，不沿用旧单的 12/18/24/36/48 元。半日仍按用户明确的日标准，不自行按小时折算。
- 有效日取“本次材料/报销范围”与“该制单人已核实参与的公出事实日”的交集，不能按申请标题区间铺满或把查到的整张公出单所有日期自动纳入。一个公出单有两日且均属本次范围才计两日；同日多事实/多单只计一次，并列明餐补唯一归属。跨日、代办或制单人与费用所属人不一致而依据不足时报告具体冲突，不能换个人、默认零餐补或套用样本 300 元；其余独立工作继续。
- 油票只作覆盖，不加进 R；票据富余不用于凑大费用。汇总单不重复计费，不借其他历史材料补覆盖。
- 必须分开建模：交通行中的公里政策部分、实际通行票部分，以及餐补政策部分。通行票绑定通行费组成项，油票绑定覆盖池；不得把整条混合交通行伪称免票、把油票硬分给费用行或删除普通全票面校验。
- 规则来源、适用场景、版本、M/T/C/R/O/F/差额、逐行输入及归属都纳入事实、计划和独立验证。新规则使用明确的新模型/版本，旧 `R=M+T` 任务不静默升级，其他类别的原约束保持。
- 写入前验证须重算已绑定的原始输入，并核对新模型 `R` 与计划主金额、费用/报销明细及银行合计相等；正常业务的真实关联分配也须闭合，历史占位按 §5 分开验证。不能只校验 coverage 声明块自身算术正确，或只信生成器已算过。油票/通行票集合和餐补日集合有唯一身份与来源，防止改大覆盖额、漏餐补或重复票据后仍通过。

### 4.5 真实公出单匹配与填写前 MD

- 唯一浏览器执行者进入真实公出单模块，按实际费用所属人、业务期间/路线定向查找，处理分页及详情。已使用的单据也须能找到，不仅在可关联弹窗中找。
- 目标人可以是申请人或实际同行人，制单人可以是部门其他成员。以详情实际参与人员和事实日期/时段、路线、事由核对，不按制单人过滤漏单，不把备注标签当事实日期。
- 读取一张公出单的全部相关事实行；允许同单覆盖多日、多票，不强造“一天一单”或“一票一张单”。每张唯一通行票须有唯一最终对应结论，并对应到 Excel 行。
- 正式费用写入前落盘 `公出单统计明细.md` 及机器记录：行程日/时段、人员及角色、路线、票号/源页/金额、Excel 行、完整公出单号、匹配依据、候选排除理由、占用状态及详情证据。逐票集合、金额及逐单分组均可复算；不把候选当已核实。
- 这份 MD 供事后核对，不是增加用户人工审批门；agent 自行完成检查。仍有未匹配或真实冲突时不能绕过写入。

### 4.6 OA 字段、逐项检查与交付

- 参考样本的 OA 类别为“差旅费”；报销明细按“交通费/餐费”区分。费用说明按真实公出日分别表达“其它交通”和“伙食”，依据当次证据核对起止日期、地点、次数/天、金额及说明。
- 不固定历史行数。每张真实关联单的本次金额按其行程的交通组成及分配餐补从原件推导；关联单据与关联明细逐单一致，正常业务再与费用明细、报销明细、银行及主金额分别核对。

- **填写前检查**从原始公里、票据和公出事实独立推导，不能把两张同样错误的派生表互比当通过。**填写后检查**独立新采 DOM，核对全部计划值、行数、身份、金额及额外/重复/缺失数据。
- 交付：整理票据目录及映射、Excel 回填副本和变更清单、公出统计 MD、逐日/逐单金额核算、实际填写结论、终局截图与证据索引。附件要有清单核对；本轮不实施上传、贴票或审批。
- 本轮统一 `fill_only`，正常填写成功按用户要求留页并报告实际驻留时限，不能许诺无限驻留；独立核验由 agent 完成，不把留页查看当内容验收前置。保存、提交、新单号、UUID、持久化和保存后重开不是本轮完成条件。

## 6. 必须固化的反例与正例

以真实探查的原件、页面快照及逐项复算为取证来源，制作白名单字段的脱敏夹具。真实样本、旧报告、原件和现有已绑定文件原样保留；不把账号、手机号、会话元数据或凭证复制进通用测试。

### 6.1 经典反例：合计相等也必须失败

以下先沿用历史餐补，仅用于定位旧单差异；不是新 30 元/天规则的期望金额。

| 对象 | 原始依据复算 | 历史单值 | 差额（历史值－复算） |
|---|---|---:|---:|
| 09-05 交通 | 146 公里＋39.90 通行费＝185.90 | 187.90 | +2.00 |
| 09-28 交通 | 132 公里＋63.86 通行费＝195.86 | 193.86 | -2.00 |
| 09-28 公出单 `12025098708` | 195.86 交通＋36 历史餐补＝231.86 | 235.86 | +4.00 |
| 12-10 公出单 `12025123375` | 188.59 交通＋18 历史餐补＝206.59 | 196.59 | -10.00 |

两条交通错误抵消，交通总额仍为 1924.93；两条关联差异累计为 -6.00，其他 7 张按原件及历史餐补核对一致。测试须同时抓出局部错值及抵消，不能只断言总额。

**关键正向对照**：`12025092018` 覆盖 09-04＋09-05，原件计算为 `191.28+185.90+30+30=437.18`，历史关联 437.18 本身正确。若只把错误的样本费用说明相加，会错误指责这张关联；测试必须拒绝这种“用错误派生值证明另一表错误”的判定。

日期反例：实际 11-12 的交通/伙食被写成 11-14；11-24 交通结束日被写成 12-24。不能按旧标签或异常跨度生成新费用/餐补天数。

### 6.2 其他必要边界

- 正确数据可通过；只改其中一格后精确拒绝，错误定位有原件/单元格/票据/公出单依据。
- 同票不同扫描、同金额不同票、单文件多票及同票多页、汇总单重复计费、漏票、去返分错、原件被改、重名文件及重复执行。
- 一单多日、多票同日、半日公出、同日多事实行，以及不含费用所属人的同日候选；申请人不是费用所属人但同行人包含时不得误排除。
- 报销单制单人、公出单制单人及费用所属人不同的情形；餐补只取本次范围与已核实参与日的交集、按日去重，查到范围外日期不能多算。新规则与历史不同餐补值分开，不把 +48 元新规则差异解释为旧关联 -6 元的成因。
- `F=R`、`F<R` 拒绝，严格富余才通过；不能用浮点容差或显示四舍五入放行。coverage 自身闭合但与原件或计划总额不符、重复油票抬高 F、漏餐补压低 R，均须拒绝。
- 至少两名人员、同名、账号切换、缓存身份不符、30 天边界、更早服务端失效、未知到期、缺扫码时间及 mtime 改动。旧 60 天记录在未满 30 天、恰满及超过 30 天分别验证，兼顾更短旧窗口；探查写回不续期、显示与执行一致。离线身份/时间模拟可用，真实登录仍须验证；不要求等 30 天或让用户组织多人现场验收。
- 旧 travel 模型与其他既有类型合法输入不被新场景误路由；未知表单/场景、模板与材料冲突、已识别但无执行能力时有明确缺口且不写入。原本非法的保存、上传、未知关联仍拒绝。

## 9. 新 session 启动、接力与恢复

本文件编写不启动 workflow、不归档旧状态、不重写根任务。用户在新 session 启动本文后，按合法入口执行：

1. 先只读核实现有状态。不能把旧 DONE run 绑定成新任务，不能冒充旧 A/B、手改 session/phase/baseline 或清失败字典。
