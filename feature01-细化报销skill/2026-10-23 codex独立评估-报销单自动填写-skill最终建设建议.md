# 企业微信 OA 报销单自动填写：skill 最终建设建议

> 日期：2026-10-23。依据当前源码、填写验收工件、63 张差旅费历史单据及原始 session 记录综合评估。
> 本文是建设建议，不修改已完成 workflow 的冻结基线，不代表已实现全部能力，也不扩大任何保存、提交或上传授权。

## 1. 最终决策

**当前保留并扩展一个业务入口 skill：`bpm-fill-run`；按报销类别维护类型资料和机器可读配置；把稳定操作、计划校验和回读核验交给共享代码。**

差旅费先接入，公出单关联与出差单关联作为两种配置预设，共用计划生成与执行逻辑。费用构成独立于关联类型，允许按本单材料组合；不按机票、铁路、住宿、餐补分别建立 skill。

快递费、研发材料费作为后续类型接入。先验证能否复用入口和执行代码；只有材料要求、步骤、判断和验收形成明显独立流程时，才拆成另一个业务 skill。当前不能宣称这些类型已经具备自动填写能力。

“查询历史单据并统计”有独立输入、输出和只读权限，可在需求重复出现后单独固化为查询分析 skill。选择组织、填写单元格、打开选择器等操作，优先维护为代码函数。

## 2. 决策依据及能力边界

| 已发现事实 | 对建设方案的含义 |
|---|---|
| attempt_026：32 项记录中 29 项匹配、零 mismatch，三项结构性留空 | 已有可靠的单一样例执行路径；不等于完整业务单据已经获审，也不等于所有差旅场景已验证 |
| 差旅普查与原底册闭合：63/63 张，均有主表及子表内容 | 足以支持差旅内部结构和场景分析；这是读取验证，不是 63 张填写验证 |
| 报销明细 163 行、费用说明 358 行、收款信息 92 行 | 执行器必须支持多行及每行独立核验，不能继续围绕固定两行样例扩展提示词 |
| 关联类型：纯公出 13 张、纯出差 48 张、混合关联及无关联各 1 张 | 两种预设覆盖主要样本；两种例外需要保留为待确认分支 |
| 多种字段差异与数据年代相关 | 优先处理可选字段和兼容性；年代相关性尚不能证明接口演化的具体原因 |
| 已有稳定 PrimeNG 操作及 no_save_guard | 复用已验证代码，逐项扩展；保留 600ms 轮询、Tab blur 与三次重读等稳定性措施 |

需要修正先前普查报告中容易被误写成业务规则的结论：

- `totalCost = Σdetails.cost = Σbanks.cost` 在本批 63 张样本中成立；`totalCost = Σcosts.cost` 仅 57/63 成立，另外 6 张 costs 为空。校验必须区分该分支，不能用无条件等式拒绝或补造数据。
- 费用构成横跨公出、出差两类，不能全部放进“出差模板内部”。公出类也存在跨日期的费用行，关联类型应由实际关联对象确定。
- `costs` 为空只说明该子表没有行，不能据此认定没有发票或附件。
- `08024` 的历史税率同时出现 0 和 3，不能写成“该科目固定 3%”。科目中文名、税率和餐补资格须有当前页面字典、正式规则或本单材料依据。
- “样本中常见餐补”“公出样本未出现住宿”属于观察，不自动成为新增餐补或禁止住宿的规则。“90% 骨架相同”没有明确计量口径，采用“主要执行结构可复用”的定性表述。

## 3. 职责如何划分

| 组成 | 放什么 | 边界 |
|---|---|---|
| `bpm-fill-run/SKILL.md` | 触发条件、输入要求、类型选择、执行入口、缺项处理、验收与交付 | 保持简短，通过明确索引按需加载当前类型资料 |
| 类型说明 `references/` | 业务含义、材料解释、已确认规则及来源、待确认项、代表案例 | 历史观察与正式规则分别标识；真实人员、账号、凭证不复制进通用案例 |
| 类型配置 | 页面字段映射、控件类型、填写依赖、适用校验、能力状态、关联预设 | 可执行映射和条件维护一个权威来源，说明文档引用配置而不复制全部内容 |
| 共享执行与校验代码 | 登录、锁、控件操作、多行处理、计划校验、回读、核账、工件与脱敏 | 固定动作由代码完成；业务不确定性显式返回，不靠模型临场猜测 |
| `team-workflow` | 冻结任务、A/B 接力、独立验收、按缺口多轮推进 | 用于能力建设和持续修复；日常成熟填写直接执行既定路径 |

建议的最小结构如下，新增文件在实际需要并有内容时再创建：

```text
.claude/skills/bpm-fill-run/
  SKILL.md                         现有入口，逐步扩展
  references/travel.md              差旅材料、规则来源及例外

automation/
  form-schema.json                 现有 UI 事实字典，按实测维护
  document-types/travel.json        拟新增：差旅映射、预设、能力状态
  fill-plan.schema.json            拟新增：本单计划的数据约定
  runs/<run>/                      本单计划、追加事件、回读与截图

```

配置文件与 schema 的具体名称可随实现调整。当前先复用仓库中的模块；同一机制在第二个类型中确认需要复用后，再提取共享模块，保持现有相对路径依赖可用。

## 4. 本单计划是连接材料、规则和操作的核心

每次任务先形成机器可校验的填写计划，再操作页面。建议计划包含：

| 内容 | 要求 |
|---|---|
| 本单身份 | 报销类别、预期登录操作人、申请人、公司；操作人和申请人分别校验 |
| 表头及行数据 | 表头、关联单据、报销明细、费用说明、收款信息；各表用行数组表达 |
| 数值与来源 | 值、来自哪份材料/哪个字段、是否明确提供或依据已确认规则计算 |
| 规则及版本 | 采用的类型配置、规则来源、schema 与执行器版本/哈希 |
| 缺项和授权 | 未确认项、结构性不适用项、用户授权的具体替代范围；无值不自动猜填 |

材料不足时集中列出需要补充的信息。只有已确定的独立部分可以继续；不能让后续联动操作依赖未确认值。

一次正常填写按以下顺序推进：

1. 解析用户材料，确认目标类别和填写范围。
2. 加载该类别资料，检查执行器是否已支持本单所需分支。
3. 生成计划，校验字段、行数、关联身份、金额关系和缺项。
4. 使用已验证的页面操作填写，按依赖关系处理选择器与只读带出字段。
5. 联动完成后重新读取实际页面，按完整单号及稳定行标识核对所有计划项和实际行数。
6. 输出一致项、差异项、待确认项和终局截图，停在只填不存状态供用户审阅。

回读应重新获取 DOM 数据，校验器按输入计划和实际页面独立比较。写入函数返回成功、进程退出码为 0、历史固定的“29/32”，均不能单独作为新单验收标准。还需检查页面是否多出非计划行，避免中断恢复或重试造成重复。

## 5. 当前代码必须先补齐的实际缺口

| 源码事实 | 建议改造 |
|---|---|
| `fill_once.py:14–30` 固定历史 run、操作人及计划路径 | 新增显式参数；新单使用独立 run，重试归入该 run 的新 attempt。保留历史样例回归入口，正常新单明确传入本单计划 |
| `_phase_fill_ng` 仅遍历费用 `row1/row2`，报销明细和银行信息只处理一行 | 改为行数组驱动，逐行执行与回读；保持旧样例可回归，禁止静默忽略超出旧结构的行 |
| `_fill_related_doc` 固定“公出”，主流程只接收单个关联值 | 参数化关联类型及完整单号，支持多张单据；对象类型与关联身份都要匹配 |
| 关联单精确匹配失败后，存在针对历史样例授权的替代路径 | 保留原授权范围，新任务无对应授权时返回待确认；不能把“改选首个公出单”作为通用默认行为 |
| 预算选择含“差旅／科技中心／年度预算项目”等样例值 | 从本单计划和类型映射取值，按每行预算身份核验；只读列由系统带出后复核 |
| 银行选择含特定银行及代码前缀判断 | 根据本单收款资料与准确银行身份选择，支持多收款行；不明确时返回待确认 |
| `form-schema.json` 是已有事实字典 | 核实并逐步接入执行映射及校验；不能假定维护一个 JSON 文件就会自动改变探针行为 |

**这些执行层缺口优先于新增独立差旅 skill。只增加模板文件，当前固定行数和固定选择逻辑仍会限制准确性。**

改动主探针后，必须先运行 `python -X utf8 stage1_probe_selftest.py` 全绿，再开展真实填写验证。扩展过程保持 no_save_guard、已验证的等待/重读及原有追加事件纪律。

## 6. 差旅费如何接入

采用一个差旅类型配置，提供“公出单关联”“出差单关联”两种预设，共享一个计划生成器与执行路径。预设决定关联对象及必要的处理分支，不决定强制生成哪些费用。

- **行数组独立组合：**关联单、报销明细、费用说明、银行收款分别建模；历史范围 1–13、1–12、0–32、1–3 仅是测试样本范围，不作为永久业务上限。
- **按材料生成费用：**餐补、住宿、机票等按本单材料和已确认规则展开；预设不得自动补入未授权费用。
- **空 costs 分支显式处理：**区分用户材料确实没有该表内容、内容未采齐和口径尚未确认；不凭历史样例自动认为新单可省略。
- **两张特殊样本留作例外案例：**混挂申请书、无关联且状态不同的单据，先确认业务口径，再决定是否增加分支。样本少不是永远人工的理由，规则未明确才是当前暂停依据。
- **填写能力单独验收：**重点覆盖超过两行费用、多条报销明细、多关联、多收款及联动重读。历史读取成功不能替代这些填写验证。

## 7. 准确性、效率与无人值守如何同时保证

### 日常成熟填写

一个执行 session 调用既定代码，加载当前类别资料和本单计划；通过自动校验、终局回读与用户审阅闭合。无须每单重新做历史普查、重新设计操作或启动多 agent 聚类分析。

### 新类型接入及复杂修复

继续使用用户需要的 A/B 接力：冻结目标、本单/样例输入、规则与代码版本、验收标准；B 实现和留证，A 独立检查原始工件。只对未闭合项推进下一轮。独立审核优先关注计划覆盖、身份、业务歧义和反例，计数、集合差集及金额复算交给代码。

同一浏览器 profile 的页面操作串行执行；另一 session 可并行读取工件和离线分析。保留 profile 锁，不以清锁方式抢占仍在使用的浏览器。

接力记录 run、attempt、计划哈希、已完成阶段和阻塞原因；恢复前确认页面身份及已有行状态。出现相同失败且没有新证据时停止盲重试，明确交接缺口。登录过期需扫码、缺失业务材料和授权边界均是可报告的人工介入点，不能承诺无限期完全无人值守。

多 agent 分析仅用于多个能独立交付、工作量足够大的子任务。此次单份 63 张数据分析使用了 7 个 agent、82 次工具调用、14 次工具报错；分析 workflow 用时约 24 分 28 秒，补齐失败维度再用 7 分 24 秒。该案例支持先采用“统一统计脚本＋分析＋独立核验”的轻量路径。没有串行对照实验，不据此宣称所有 workflow 都慢或给出未经验证的加速倍数。

### 全程不变的边界

- 当前只填不存：保存、发送、流转、提交、上传、暂存、贴票、审批等禁点；填完停在待审状态。
- 活体凭证仅用于受控登录与内存内请求，不进入普通工件、日志、报告或 git；输出按白名单组织，截图及业务数据只保留任务所需范围。
- events.jsonl 追加，结论以实际页面回读、截图和运行结果为准。
- 历史案例单号仅作案例；目标匹配使用完整身份。部门、预算年度、组织和科目不跨任务沿用旧样例默认值。

## 8. 实施顺序和完成标准

| 顺序 | 交付 | 完成标准 |
|---|---|---|
| 1 | 本单计划约定＋参数化入口 | 新单不依赖旧计划/固定人员；缺字段、未知配置或不支持的分支在填写前可被发现；历史样例仍可回归 |
| 2 | 差旅执行能力扩展 | 多行费用、多行报销明细、多关联类型/单号、多收款分别通过代表案例验证；完整回读，不静默跳行或换单 |
| 3 | 固化 `bpm-fill-run` 与差旅配置 | 新 session 只读入口及当前类型资料即可执行已支持任务；未支持或待确认分支如实返回 |
| 4 | 接入第二类，优先考虑近两年 23 张的快递费 | 先读取代表历史单和用户材料确认流程，再做真实只填不存验证；以此检验复用边界，随后接研发材料费 |
| 5 | 按实证提取共享模块、完善接力 | 修复一个控件能惠及已接入类型且通过相关回归；失败能依据工件继续，避免重新探索整个流程 |

测试围绕真实差异和曾发生的失败设计：多行不丢失、不重复；关联身份精确匹配；联动后重读；空表条件；金额条件；缺材料停止；凭证不落盘。类型配置记录“只读已观察／填写已验证／待确认分支”等能力状态，skill 只承诺已验证范围。

日常运行分别记录解析与规划、页面填写、回读核验耗时及人工介入原因。以无差异完成率、缺项发现率和稳定复用情况评估效果，不以 skill 数量或 agent 数量评估成熟度；不给不同大小单据设同一个未经实测的耗时承诺。
