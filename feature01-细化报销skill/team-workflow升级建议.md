## 3. 已有能力应继续使用

本次只读核查确认以下机制已存在，升级不应再实现一套：

| 已有机制 | 当前落点 | 对建议范围的影响 |
|---|---|---|
| 唯一后台 wait、原生通知、醒来先 status、超时静默重挂、重复通知处理 | team-workflow/SKILL.md；workflow.py 的 wait 单 waiter 锁、seq/phase 检查和 Windows event | U5 只补异常分类与重新进入的说明 |
| 先保存状态再通知、seq 递增、监听前检查最新状态 | workflow.py 的状态保存和 wait 路径 | “不丢唤醒”作为维护现有行为，不新建事件机制 |
| 冻结基线、绑定 A/B、原 session resume、终态 archive | skill 与 helper 共同限制 | 非终态孤儿交由外部维护，保留现行绑定边界 |
| 同 run 失败次数不得回退、跨轮承接 failure_key | team-task 与 workflow.py | 不另造失败账本；跨新 run 的历史仍须明确交接，不能假称 helper 已自动继承 |
| 交接状态、合同链、P6、所列工件/证据哈希及逐项判据核验 | workflow.py 的 finish/review | U2 修使用方式，不新增重复的全量哈希门禁 |
| 按依赖和所有权评估拓扑，复核强度与拓扑分开 | team-task/funnel-gate.md | U3 是改进选型依据，不新增评分体系 |

继续保留双独立 session 常驻、唯一 Bash `run_in_background:true` helper wait（3600 秒）和原生通知；单 profile 单执行者，重型任务错峰。A 负责全局目标和独立验收，B 依据自足任务实施。保存、提交、凭证、业务 registry、人工门与失败预算均沿用现行边界。

独立审查确有收益：旧轮次发现并处理过构建源清单遗漏、金额断言缺键导致自比恒真、事实反序列化校验不足；V3 新 session 验收中的三次视觉误读也被机读与汇总互证纠正。效率提升应保留这类发现问题的能力。

## 4. 六项建议的具体范围

### U1：工作包覆盖必要配套，先说明用户链路

在现有派工段落补三个短检查，不新增表单：

1. 用户最终结果中，本轮要补哪段尚缺证据的链路？
2. 已有材料、候选号、能力和阻断记录能复用什么？历史入口不能替代当次身份、材料及业务事实核实。
3. 本轮功能所需的源码、schema、配置、测试、构建清单和使用说明是否已明确授权？

任务仍明确责任文件、共享文件协调和禁止范围。已知必要配套在派工时一起列入；新发现的越界需求走现有增补程序，不能用“必要连带修改”概括授权认证、安全守卫、保存行为或全局 skill。

材料和登录具备时，优先验证最小真实业务链；缺外部条件时继续独立可做部分。无需为了贯通最小链提前扩展所有类型。

**观察是否有效：**下一项类似工作包不再因已可预见的配套文件漏列而专开补授权轮；并能说明对最终用户结果的实际推进。

### U2：交接内容先定稿，再计算引用哈希

本次找到的三个具体例子：

| V3 轮次 | 实际问题 | 最小改进 |
|---|---|---|
| 第 2 轮 | finish 返回 `EVIDENCE_REQUIRED`，handoff 缺非空 evidence 列表 | 示例明确证据列表必填，并使用本轮实际路径 |
| 第 3 轮 | 重建 team-progress 时漏 contract_id / effective_contract_id，补回后重算哈希 | 沿用已有进度骨架，保留必要头字段 |
| 第 6 轮 | finish 返回 `TEAM_P6_NOT_COMPLETE`，漏唯一漏斗 P6✓ 标记 | 按真实完成情况落实 P6 标记后再生成 handoff 引用 |

建议只补一段准确示例/短清单：**先完成真实工作及 P6 → 定稿 progress 必需字段、状态和标记 → 填写 summary、evidence、failure_counts → 生成工件哈希 → finish**。按执行结果填真实状态，不能为过门禁机械勾选。

若门禁报错，按具体错误补正后更新受影响引用；不手改 workflow state。上述哈希重绑发生在文件补正之后，属于正确保护行为，没有证据表明 helper 擅自改坏了哈希。

现有 finish/review 已检查所列路径、哈希和合同链。暂不增加“预检查脚本”、第二套 manifest 或新的状态节点；只有以后发现现有校验未覆盖的反复语义错误，才评估一个针对性断言。

**观察是否有效：**下一次真实交接不再因上述格式遗漏试错；现有错误输入仍能被门禁拒绝。

### U3：有独立工作块时，再派临时实现 agent

在现有拓扑理由中增加一句：

> 先按输入、依赖和文件所有权检查能否分工，再决定 lead 独做；不能用“我计划全部自己做”证明任务只能串行。

有输入明确、能独立落盘、整合成本较小的工作块时，可试用一个临时实现 agent。例如材料事实与接口明确后，Excel 副本处理与覆盖模型负例测试可评估拆分。这里只是候选划分，不是已证明的提速结果。

低风险、范围清楚的盘点和格式核查可选低成本模型；涉及业务规则、金额语义和关键验收时按能力与风险选型。分派须写明输入、文件所有权、交付物及禁止范围，告知同仓库并行修改情况。lead 负责整合，实现者不作自己产物的唯一终审。

真实 OA 单 profile、依赖前一步输出的写入/回读继续串行。额度或资源不足时减并发，不默认增设 planner，不强制每轮派人，也不为“展示并行”复制同一项重型测试。

**观察是否有效：**一项合适的真实任务中，独立产物可直接整合，且没有引入明显冲突、重跑或关键路径等待；不达此条件就保留 T3。

### U4：把审查重点写清，用好已有证据复用

在现有审查摘要中简短区分：

- 本轮新增或因变更重新验证的证据。
- 仍适用的既有独立证据及其原验证时间、范围。
- 具体缺陷、尚未开展的后续阶段或外部阻断。

A 侧重用户目标、跨轮遗漏和业务证据；临时 reviewer 侧重指定技术风险、原始数据重算和冻结产物。复核任务应写清问题，减少无意重复，不撤销现行合同要求的 fresh 终审或必要交叉复核。

V3 第 8 轮已因源码/schema/测试未变而沿用第 7 轮构建；这是已有实践。复用需相关依赖和证据有效、环境适用、没有未解差异。登录身份、当前页面和终局 DOM 仍须当次核实；旧证据不能表述成“本轮重新运行”。

保持全部判据覆盖和现行每轮重读冻结基线规则。暂不引入判据缓存或修改验收状态机。报告里的 `rework` 包括阶段合格后继续派工，不能直接统计为缺陷次数。

**观察是否有效：**读者能分清阶段推进、真实返工、新验证与旧证据引用；不因写法简化丢失验收依据。

### U5：wait 异常先分类，恢复沿用现有入口

原始通知证实：旧运行至少三次、新 V3 至少一次，Claude Code 报告因系统低内存而停止空闲后台 wait。此为宿主通知所述原因，未另做 OS 内存遥测；不能进一步归因到 VS Code。通知还要求等请求后再重启，不能建议 agent 收到这类通知后立即无限重挂。

只补一小段处理说明：

- 正常 TIMEOUT、已有 waiter、重复通知：继续按现有规则处理。
- 收到异常退出通知：先 status，记录任务 ID、错误类型和阶段；遵守宿主停止指令，避免错误自旋。
- 收到明确重挂/resume 请求，或上下文恢复进入原有入口时：先 status 核对角色、轮次和阶段；再结合原后台 task_id 的通知或任务状态确认 waiter。status 本身不证明 waiter 存活；仍在则沿用，确已消失且宿主允许重挂才恢复唯一 wait，状态不明时不创建第二个。
- 宿主已退出或无可处理通知：由下次入口恢复，不能声称后台仍在持续运行。配额等待与业务缺陷分别记录。

先改善错误说明与恢复指引。若以后复现 helper 本身的具体缺陷，再修对应分支；不改成定时轮询、常驻监控、自动杀进程或无限重试。

**观察是否有效：**在隔离小任务中，正常等待与恢复不产生第二个 waiter；异常原因及下一入口明确。低内存回收本身不承诺由 skill 消除。

### U6：外部 agent 维护，保留精简指南框架

**用户已确定：孤儿恢复直接交给外部 agent，team-workflow 无需内建通用机制。** 当前“原绑定 session resume、终态 archive”的边界保留。10 月 26 日的维护实例说明外部处置已有可参考路径，无需将这类例外扩成日常工作流能力。

建议指南直接保留在本节，约半页，发生事故时再交给外部 agent；暂不另建技能、脚本、恢复命令或测试矩阵。框架只含四步：

1. **只读定位。**读取当前 state、最后交接及工件，核实原 A/B、waiter、相关写入进程、业务锁/registry 和未保存页；判断原 session 是否可恢复。状态不明时保留现场，不能凭窗口消失判定孤儿。
2. **确认维护范围。**根据当次明确授权列出拟迁移文件和回退位置，动手前复核现场未变、相关写入已静止；不覆盖新草稿或新 run。已有授权覆盖时不重复询问，单纯 status 请求不授权迁移。
3. **归档后退役。**先保留旧调度文件原字节、哈希、失败历史和在途成果，确认归档可回读，再移出确定归属旧 run 的活动文件；中途失败依据记录恢复或保留现场。不动业务原件、registry、活页或凭证，不将旧 run 改成 DONE，不冒用原 session。
4. **交接后正常重开。**记录旧 run 为未完成退役、实际迁移项与回退条件；新首轮自足承接成果、未解事项及 failure_key 历史，沿正常入口创建新 run，不通过重开解除熔断、人工门或保存限制。

具体操作依据当次现场制定。参照 [10 月 26 日维护与交接记录](2026-10-26%20V3工作流启动阻断修复与交接.md)，其中固定 run 的脚本不是可复跑的通用命令。指南不预先授权未来迁移，也不因再次出现事故自动触发内建机制开发。

**完成标准：**外部 agent 能据此定位现场、保留可回退证据并交接未完事项；实际维护结果单独留证，日常 team-workflow 不增加步骤。

## 5. 验收按改动范围安排

| 将来选择的改动 | 相称的验证 |
|---|---|
| 只改派工/交接示例和报告说明（U1—U4） | 对照上述真实漏项核对示例，在下一次获授权任务中观察；不为文档改动专造多轮施工 |
| 改 wait/helper 执行行为 | 运行受影响测试，并用真实 Claude-GLM 双独立 session 的隔离小任务验证通知接力、超时及恢复；不伪造 A/B 身份 |
| 精简外部维护指南（U6） | 对照已有维护实例核对边界与交接要求；实际处置按当次现场留证，不新增内建恢复功能验收 |
