## 6 第一项 快递费扩展计划

### 6.1 材料和业务口径

以三张代表历史单了解结构，再依据本次真实材料确定填写值。需要识别的材料包括费用统计 CSV/XLSX、快递发票及其明细、结算清单或其他用户实际提供的业务凭据；不能要求每单都存在全部材料。

形成以下关系：本次统计行 → 可定位的运单或结算记录 → 发票或有来源的免票依据 → OA 主要费用行 → 报销明细 → 收款金额。材料未包含运单号时不补造；如无法确认费用归属或重复关系，应集中列缺口。

重点确认三种问题：

1. 一张汇总发票对应多笔快递费时，是否按真实材料合并或拆成 OA 行；禁止同时计入结算合计和它的明细。
2. 多张发票、多个结算清单中是否包含相同运单或同一费用；区分发票扫描重复与真实多笔金额相同的业务，不能只按金额去重。
3. 月份、实际寄件日期、付款对象及报销期间如何对应；不沿用历史模板日期、收款人或旧单费用摘要。

字段与规则表中区分“历史观察”“当前页面事实”“本次材料事实”和“用户或正式制度规则”。不能把历史上常用的预算、费用项目、免票处理写成所有快递费的固定默认值。

### 6.2 配置和执行

1. 新增 `express.json` 和 `references/express.md`，依据实际字段配置精确类别、项目、预算和收款选择方式。
2. 将任务入口、计划校验、模板读取、run 绑定和保存控制器接入 `express`，保持 travel 原路径可用。
3. 确认关联表和费用说明表是否适用。为空必须有本单来源支持的不适用声明和理由；页面隐藏、读取失败、未加载不能直接当空表。
4. 若快递费没有差旅日期、地点、天数列，按新类型列集合处理，不能填虚构日期或套用差旅字段凑齐 schema。
5. 选择报销类别后，等待页面联动稳定，重新识别表、列、默认行和预算字典，再填写。自动带出的预算部门、预算项目和银行信息必须读回核对。
6. 按实际材料建立主要费用行金额口径，保持 `totalCost = 报销明细合计 = 银行合计`，费用说明适用时按声明语义与总额闭合。
7. 发票分类、身份去重、原件及复核 JSON 哈希、分配覆盖和不同来源一致性继续执行；快递类别不获得更宽的免票或来源豁免。

第一版优先完成经实证确认的普通全额报销。若代表单出现关联采购单、产品表或其他新业务结构，应登记并决定是否属于本次承诺范围；不能删除这些数据后把该样本当作成功案例。

### 6.3 离线测试

至少覆盖真实差异和必要反例：

| 场景 | 期望结果 |
|---|---|
| 单笔快递费、整张发票、一个收款人 | 正确生成计划并完成本地执行及独立核对 |
| 多笔快递对应一张汇总发票，或多张票对应多行 | 每笔有来源，行与发票分别闭合，没有重复计入 |
| 超过两行的明细或费用说明 | 无漏行、重复行和错位；末行核对纳入终局 |
| relations/costs 确认不适用 | 按配置和本单声明处理，不强造差旅行；页面实际多出行则失败 |
| 运单号、发票号或银行账号有前导零 | 保持字符串和原值 |
| 同票不同扫描件、结算表与发票冲突、缺票据分类 | 在浏览器写入前阻断 |
| 类别、模板、配置或保存授权错配 | 在写入或保存前阻断，不能回退 travel |

本地 DOM 应贴近已经观察的真实列、弹窗、只读回显和异步联动，不能再用一个总是成功的选择器替身证明真实选择器可用。

### 6.4 真实网页验收

选择一笔本次真实快递费业务，用户提供完整模板号、材料目录、报销说明、操作人，以及对该笔新建和保存草稿的具体指令。优先选择自然包含多行结算或多张发票的任务；没有多行时不人为拆分凑场景。

在真实 OA 中完成：准确进入新单 → 选择快递费 → 观察类别联动 → 真实项目/预算/银行选择 → 所有计划行填写 → Tab 失焦和稳定回显 → 完整独立 DOM 回读 → 保存前截图及复核 → 专用控制器执行一次精确保存 → 取得唯一单号与 UUID → 重新打开 → 全量持久化回读 → 确认未提交。

保存成功后，再对同一 task_id 进行只读恢复核实，证明不会再次新建或保存。不得用再次保存作为重试测试。

通过标准为本计划第 8 节全部通用项，以及本类承诺的场景项。交付真实单号、金额、未提交状态、run/attempt 和证据路径；未覆盖的分支逐项列出。

## 7 第二项 研发材料费扩展计划

### 7.1 先确定材料明细所在层级

定向读取三张代表历史单，同时核对本次真实采购材料。先回答以下问题，再确定 schema 和执行改动：

| 必须确认的问题 | 对实现的影响 |
|---|---|
| 材料名称、规格、数量、单价、单位、总额放在费用说明、产品表，还是仅在附件中 | 决定执行表、字段和回读范围，不能凭类别猜测 |
| 是否存在采购申请、订单、合同等关联 | 若存在，需要准确关联类型、完整单号及相应明细语义；不能借用差旅关联枚举 |
| 页面“金额”表示单价还是整行总额 | 决定 Decimal 复算与发票分配基数 |
| 发票、采购统计表、付款记录各自包含含税/未税、折扣、运费或尾差的哪些内容 | 决定是否能够闭合，不能默认某种税率或舍入方式 |
| 收款对象是员工还是供应商、是否分多行付款 | 决定身份和账户核对，不能沿用个人报销账户 |
| 是否有借款冲抵、部分票面报销或新附件操作 | 现有不支持项保持阻断，不能暗中并入普通全额报销 |

“发票上有数量单价”与“OA 必须按单价乘数量存储”是两件事。若 OA 接受行总额，可以基于发票整行金额核对并保存材料明细来源；若 OA 要求单价与数量，则必须实现相应金额语义。不能把所有数量单价票据一律标为免票，也不能擅自把 OA 应填的明细压成一行。

### 7.2 普通全额材料报销

新增 `rd_materials.json`、`references/rd-materials.md`，复用快递费阶段完成的类型注册和绑定。

对于实测只需普通明细、预算、收款和行总额的场景：每条材料费用对应本次可定位的材料事实；票据按全额分配到主要费用行；产品表为空须经过完整读取确认，并有适用范围说明。不得从历史模板复用本次材料名称、数量、日期、供应商付款事实或金额。

预算科目、费用项目、预算单和只读带出的部门/项目应逐行核对；多个材料品类不默认共用第一行科目。账号、发票号及业务编号保留前导零。

### 7.3 数量单价和产品表的扩展分支

这部分由真实样本决定是否是本次必须实现的主流程。若代表单和用户待办业务普遍需要这些字段，必须纳入研发材料费交付，不能以只做最简单样本代替整个类型。若本次业务确实不适用，可以先验收明确的普通全额子范围，其余分支保持未实现或待验，不宣称全场景支持。

数量单价需要实现时，工作应同时覆盖：

1. 在配置和 schema 中明确数量、单位、单价、行总额及金额语义；金额使用 Decimal，精度与舍入依据票面和已确认业务规则，不能套用浮点计算或默认忽略一分钱差异。
2. 票面列示行总额是独立核对依据。数量乘单价与行总额不一致时，检查折扣、税额和舍入来源；无法解释就返回缺口，不改写票面金额。
3. 发票分配比较的是有效行金额。若 `cost` 字段存单价，不能把该指针的单价当作整行金额；分配、数量来源和行总额关系必须有可验证契约。
4. 更新材料对账、计划验证和页面终局验证，并增加非整数数量、多行、多票及尾差冲突的反例。终局使用独立 DOM 中的数量和金额重新计算，不复用写入函数的成功返回或缓存结果。
5. 若原有 `cost_amount_semantics=unit_price_times_count` 被采用，必须解决当前发票对账只支持 `line_total` 的限制；不得删除该限制却不增加等价的有效行额核验。

产品表需要实现时，必须一次补齐：模板读取白名单、版本化行结构、来源指针、页面编辑器、独立快照、金额关系、保存后持久化核对和反例测试。原有 `UNMODELED_BUSINESS_ROWS` 保护保留给其他未建模数据，不能全局忽略 products。

若扩展到第五张执行表，需同步修改 schema、`bpm_plan.py`、UI 行调度、独立采集器、校验器、材料费用分配和测试中的固定四表假设。先写清产品金额与 details/costs 的归属关系，避免同一费用在不同表重复相加。

部分票面报销、借款冲抵、附件上传、贴票和提交不随研发材料类型自动开放。本次材料落入这些分支时，报告具体受限行和材料；不要改为全额、改银行金额或删行来通过。
