## 2 开工顺序与不变边界

施工按下面的顺序推进：离线检查先排除可预见错误，随后直接到真实网页验证相应控件与整单路径。当前已获真实测试授权，不以“只允许离线验证”或“尚无另一张正式业务单”为由停止真实回归：

1. 闭合核验缺口，建立清晰的真实页面能力基线。
2. 固化本次真实控件操作，接回正式执行入口。
3. 让程序连续执行，正常路径不再逐格等待模型发命令。
4. 根据新计时减少重复动作和扫描，完成同口径对照。
5. 在本次真实测试授权下验收正式入口的整单填写及 C0/C1 耗时；自动保存按具体任务授权另行核实。

全程沿用 AGENTS 的 profile 独占、直连网络、凭证保护、追加事件及历史工件只读规则。不得删除 task registry、修改旧 run、覆盖用户已保存的样张、强关其他 session 的页面，也不能用更换 task_id 绕过任务意图。浏览器仍被原 session 占用时先正常交接，不删活锁抢占。

本轮不改 600ms 防御轮询、Tab 失焦与既有重复回读机制，不改全局超时。可以针对已确认失效的控件做局部存在性守卫，为具体动作设有依据的局部超时；必须保留业务后置条件。不得使用 force/JS 点击、DOM 赋值、移除 readonly 或直接写接口提速。

## 3 第一阶段 闭合核验并固化真实控件

### 3.1 修复会影响保存判断的核验缺口

主要改动 `bpm_verify.py`、差旅配置、必要的快照与计划约定，以及相关验证用例。

**关联明细漏检：**此前独立复核已经复现，计划有 1 条关联，实际 `detailrels=[]` 且 completeness=true 时，核验仍通过，模拟保存控制器甚至返回成功。原因是空表被 `if not rows: continue` 跳过。修复后对已声明投影先检查存在性、类型与期望行数，空表也要参与比较；不能仅检查“表已读取”。[复现工件](../automation/offline-verify/20261023-independent-check/review_repro_empty_detailrels.json)。

**系统只读字段空值：**查清本次 9 项空字符串的页面/API含义及适用关联类型，在字段配置中明确“必填数值”“允许空的系统回显”“尚未支持的分摊”等状态。只有获得字段级依据，才允许相应空值分支。保留原始观察，不把整个快照中的空字符串一律转成零。非零、格式错误、应有值却缺失、未知分支都继续拒绝。

本次使用的一条关联可能对应一条或多条明细，不能将演示中一对一的投影永久写成所有差旅的业务规则。先明确正式支持的一对一范围，其他分支提前报告；如增加多明细分配支持，计划必须包含完整明细身份与分配金额，并分别核对。

验收至少包括：关联存在但明细为空时拒绝且保存点击数为零；合法系统空值按已确认字段规则处理；缺表、错号、重复明细、非零未支持分摊均不能被“空值兼容”放行。演示最终快照应成为固定回放案例，保留原结果，另产出修订后规则的验证工件。

## 4 第二阶段 连续执行与减少重复操作

### 4.1 正常填写由一次程序调用连续完成

保留“材料理解与计划生成由 agent 完成，确定页面动作由程序执行”的职责。计划准备阶段集中核对材料、身份、关联可用性及已知业务冲突，形成来源明确的计划后，再进入正式执行。

正常路径为：

```text
准备及校验本单计划
  → 一次启动 fill_once 正式执行
  → 身份与页面检查
  → 关联及明细金额
  → 费用说明
  → 报销明细及预算
  → 收款及支行
  → 完整独立核验
  → 按本次授权停在待审或受控保存
```

程序按阶段输出小型进度与异常摘要，模型按需读取进度。正常控件动作不再通过 command.json/response_N.json 逐格派发。材料解析或缺项确认可有模型交互，不将“减少模型往返”误写成绕过用户业务判断。

失败时先返回明确的控件/阶段、当前页面身份、已完成范围和证据。已知且有状态变化依据的瞬时失败，允许有上限的局部重试；相同错误没有新证据时停止自动循环。未知控件进入显式诊断与修复，再通过局部验证，不在普通填写中无限追加补丁。

同一进程、同一活页内可根据新鲜回读跳过已一致的行或字段。全局恢复规则仍保留：本轮不建设浏览器重启后的未保存单自动恢复，也不改变已有保存意图的只读核实规则。

### 4.2 在同一编辑器内完成写入

先埋点确认各字段实际动作链，再去除重复工作。重点检查：外层为了识别控件双击一次，内层通用填写函数又双击；已经存在可写 input 仍重新激活；显示值仅有金额或日期格式差异却被判需要重写。

- 编辑态已建立时直接使用当前原生控件完成对应动作，保留提交/失焦和既有回读；不要再次走完整激活循环。
- 只读与系统带出列按配置跳过写入，仅在依赖操作后核对。不可根据“当前没 input”推断只读。
- 用既有字段类型归一比较金额和日期，账号、完整单号、人员及选项身份保持严格匹配。
- 连续完成一行内已支持的操作，不在每格之间返回模型；页面写入保持串行。

本次 46 个 `cell_input_write` 计时合计约 1.16 秒，51 个 `cell_activate` 合计约 74.94 秒，两类计时不是完整流程且存在外围动作。它们提示应检查激活、页面操作与等待，而不是优化 Python 数字计算；不能据此承诺可节省某个固定秒数。

### 4.3 减少重复扫描和诊断开销

`bpm_ui.py` 当前单字段操作多次调用全表映射及整表回读。改为阶段内复用稳定的表/列结构，在增行、表单切换、选择器导致重建后主动失效；控件句柄和 nth-of-type 路径不跨重建复用。写入后的值仍重新读取。

来源解析及计划检查可以在准备阶段复用同内容哈希的解析结果，避免为每格重新读整个 Excel 或重复解析相同文件；计划、材料、配置在执行阶段边界和保存前仍按要求复核。任何缓存都不能替代最终独立 DOM 回读或保存前验证。

保留各阶段、失败现场、最终回读及保存前后的必要截图。相同错误且状态未变化时复用已有诊断引用，避免反复全页截图和长 DOM 输出；事件继续追加。材料路径、业务敏感值及凭证的处理规则不变。

## 5 第三阶段 可复算计时与验收

### 5.1 先建立新的可比较基线

本次 28 分钟是现场开发型演示，优化后不能仅与它比较就宣称执行器加速若干倍。先记录固化正式控件但未进一步优化动作的 C0，再记录减少重复操作后的 C1；记录源码、配置、计划与材料哈希、单据规模、身份分支、网络条件及缓存状态。

在现有事件基础上增加以下区间，不重复建设第二套日志：

| 区间 | 边界与报告方式 |
|---|---|
| 准备 | 模板读取、材料解析、计划生成与校验分别计时 |
| 登录 | 浏览器启动、登录态复用、人工扫码分别记录 |
| 页面执行 | 新建导航前 UI_START → 完整独立核验结束 READBACK_END |
| 阶段与动作 | 关联、费用、预算、银行；激活、面板打开、查询、选择确认、写入、失焦、回读，保留嵌套关系 |
| 保存 | 保存前复核、一次点击、只读核实及重开回读，按具体任务授权单独报告 |
| 人工及调试 | 业务确认、等待审核、诊断和代码修补单列，不能混入稳定执行耗时 |

记录已完成动作、重试、失败、模型介入次数、额外诊断命令数与页面往返次数。外部命令响应数与模型调用数分别统计。按相同起止事件复算顶层耗时、嵌套区间并集和未覆盖区间；未覆盖部分不擅自归因。
