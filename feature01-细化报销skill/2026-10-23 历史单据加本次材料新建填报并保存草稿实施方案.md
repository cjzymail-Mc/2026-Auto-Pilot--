# 历史单据加本次材料新建填报并保存草稿实施方案

日期：2026-10-23。状态：待实施。本轮只编写方案，不修改执行代码，不新建或保存实际报销单。

本方案承接[skill 最终建设建议](2026-10-23%20codex独立评估-报销单自动填写-skill最终建设建议.md)，把目标进一步明确为：用户提供历史模板单号与本次材料目录，agent 完成新单填写、核验及草稿保存，停在待用户审核状态。优先完成差旅费的一条完整路径，再用第二类报销验证复用能力。

## 1 目标任务与权限

用户希望日常这样交代：

> 你查看编号 XXX 的报销单，以该报销单为模板，然后根据我整理好的文件（发票、费用统计 Excel 等，路径位于 XXXX），帮我新建一张报销单并完成填写和保存。完成后不要提交，保存好等我审核即可。

一次正常任务应当得到：一个可重新打开、内容经核对的新草稿单，及其单号、金额、材料清单、核验结果和保存后截图。若需要补充材料或处理业务冲突，一次集中说明缺口；已授权且信息完整的部分自主执行，不重复索要例行确认。

| 动作 | 执行口径 |
|---|---|
| 查看指定历史单、读取本次材料、生成计划和新建填写 | 属于上述具体任务的授权范围 |
| 保存新草稿 | 具体任务明确要求保存时允许；保存前完整核验与截图，保存后验证确已落库 |
| 未要求保存的填写任务 | 默认只填不存，不从本方案推导所有任务均可保存 |
| 提交、发送、流转、审批、终止 | 继续禁止；禁止点击“保存并提交”等复合动作 |
| 发票识别、上传、贴票、导入附件 | 本地读取文件不等于上传授权；现有禁点边界继续适用，确需上传才能保存时报告具体阻塞 |
| 修改或覆盖历史模板单 | 禁止；只读模板，另建新单 |

本轮用户明确了产品目标，后续实际任务按其具体指令确定操作范围。新 session 若只收到建设指令，没有真实模板单号和材料路径，应推进开发与离线验证，不虚构一张生产单作为验收。

**旧成功样例不能直接拿来验收自动保存。**旧 `fill_plan.json` 中报销明细金额为 191.40，费用说明合计及收款金额为 251.40，存在跨表金额差异。逐字段“写入等于计划”不代表金额关系正确。先查清口径或取得本次有效材料，不能为通过新校验而改写历史证据，也不能把不闭合计划送入保存。

## 3 整体流程与职责

```text
用户指令
  → 任务范围与材料清单
  → 精确读取历史模板
  → 解析本次 Excel、发票及说明
  → 生成本单计划并校验
  → 新建表单，按依赖关系逐表填写
  → 独立重新回读全部计划项、实际行数及金额
  → 保存前截图与证据
  → 保存草稿
  → 确认新单身份，重新打开并再次核对
  → 返回待审核的新单及工件
```

继续保留一个 `bpm-fill-run` 业务入口。Skill 负责理解任务、选择类型资料、解释缺项与组织交付；确定的页面操作、校验、保存和证据由代码完成。差旅的公出关联与出差关联采用配置分支，不按机票、住宿、餐补拆 skill。

### 历史模板与本次材料如何取值

历史模板提供表单结构、费用项目写法、预算与收款等可复用信息；本次材料提供本次日期、行程、发票、金额、说明和应关联的单据。历史数值及关联单不得自动变成本次费用事实。

对申请人、公司、部门、支付方式及收款资料等稳定字段，可以在“以该单为模板”的范围内沿用，但必须核对本次适用身份与当前可选项，将沿用来源写入计划。普通沿用不反复询问；身份不符、材料冲突或候选不唯一时集中确认。

显式用户说明优先于模板默认。Excel 汇总与发票属于相互核对的来源，冲突时不能静默选择一方。模板中的单号、UUID、流程状态、旧日期、旧发票身份和系统生成信息不得复制成新单身份。

### 本单计划与证据

每个新任务生成独立 run；同一任务重试使用新 attempt。计划至少包含：

- 完整模板单号、读取时间与快照哈希；预期操作人及申请人分别记录。
- 单据类型、表头，以及关联、报销明细、费用说明、收款的行数组和本地稳定行标识。
- 每个关键值的来源：材料路径、Excel sheet/单元格、发票页码或模板字段；推导值记录计算依据。
- 类型配置版本、材料哈希、计划哈希、未确认项、不适用项及具体任务授权范围。
- 保存策略：`fill_only` 或 `save_draft`；提交始终不在本流程中。

建议新增 `automation/fill-plan.schema.json` 与 `automation/document-types/travel.json`；实际模块命名可按现有代码合理调整。schema 校验之外必须有业务语义校验，不能仅检查 JSON 形状。

材料解析的产物与计划分开保存，原始材料只读。支持先从 Excel/CSV 读取结构化费用，再用 PDF、图片发票核对；使用环境已有的文档、表格和图像读取能力，不在本轮建设通用 OCR 平台。银行账号、完整单号及发票号码按字符串处理，避免前导零丢失和科学计数法。识别不清的关键值列为缺项。

## 4 分阶段施工与验收

各阶段在同一目标下依次推进，不把完成第一阶段视为整项完成。能独立进行的代码与离线验证不等待生产输入。

### 阶段一 参数化入口与计划校验

1. 改造 `fill_once.py`，接收本单计划、预期操作人、独立 run 或重试 run，以及驻留参数。无参数不得继续默认填写旧样例；旧样例仅保留为显式回归模式。
2. 定义 task 输入与 fill-plan 的区别：task 提供模板单号、材料目录和本次说明，fill-plan 是读取解析之后的可执行结果；通过 skill 调用现有或新增脚本串起来，避免把自然语言理解硬塞进固定脚本。
3. 建立材料清单与模板快照。先复用已验证的只读 DOM/GET 路径，按完整单号确认唯一目标；没有快照则精确读取，不要求重新普查全部历史单。
4. 新计划使用行数组；旧计划可由明确的兼容转换读取，不能因旧 row1/row2 结构限制新单行数。
5. 增加缺项、字段来源、身份、重复材料和金额的前置校验。扫描到多份同内容文件先去重或说明，不能按文件数直接生成费用行。

验收：不同操作人、不同模板单号、不同材料路径可以形成独立计划；错误身份、未知类型、关键缺项、冲突金额和不支持的分支在新建填写前被发现；历史工件不改写。

### 阶段二 多行填写与完整独立回读

1. 费用说明、报销明细、关联及收款分别由数组驱动，逐行执行并保留结果；支持公出与出差关联，严格核对完整单号与对象类型。
2. 按依赖处理预算选择和只读回显，预算目标来自每行计划；按准确收款人与账号、银行/联行号处理银行选择。移除新任务中的旧样例默认值，不放宽匹配规则制造通过。
3. 新建前及重试前确认当前页面身份与已有行数，避免重复添加。中断恢复先盘点页面；已保存的任务只读检查已落库结果，不自动再新建一单。
4. 联动结束后重新读取 DOM，独立比较计划与实际页面。检查字段覆盖、行数、漏行、额外行、重复行以及行身份；不能只复用写入函数保存的 readback。
5. 金额使用 Decimal 等精确十进制算法，并区分行金额与单价乘数量，不对未确认口径重复乘算。

金额规则先明确表间含义再实施。历史 63 张样本中，totalCost、报销明细之和及收款之和闭合；费用说明之和在有行的 57 张闭合，另 6 张为空。空表需区分本单确实不适用、材料缺失和未采齐，不能无条件要求费用说明求和，也不能凭历史空表自动放行新单。

验收：超过两行费用、多行报销明细、多关联、多收款及空费用表分支有针对性的离线验证。对最终数据中的错金额、错账号、错关联、多余行、遗漏行，独立校验能拒绝。当前 submitType 留空的样例行为不能作为新保存任务的默认：本次必填类别等必须从有依据的计划取值。

### 阶段三 受控保存草稿与落库验证

这是单独验收的执行能力。不得简单从 `NO_SAVE_WORDS` 删除“保存”，也不得通过通用点击助手或直接写接口绕过守卫。

1. 实现仅供该阶段调用的保存控制器。它核对本次任务保存授权、计划哈希、当前新单页面、完整回读结果和无阻断缺项；只接受明确的“保存”按钮，不接受“保存并提交”等近似文本。
2. 保存前落盘全部回读及终局截图；保存控制器自行复查当前状态，避免依赖一个可随意传入的 `verified=True` 标记。存在变化则重新核验。
3. 先确认实际页面的保存按钮、对话框与保存后的状态含义；只观察模板页或离线 DOM 不能宣称真实保存语义已验证。未识别的确认框不自动确认，含提交/流转语义的动作拒绝。
4. 仅经 UI 保存草稿，使用已观察的只读路径确认新单完整编号/UUID与未提交状态。不能仅凭 toast、HTTP 200、按钮变灰或进程退出码判成功。
5. 重新打开该新单，按计划再次核对金额、关键身份、所有明细与行数，证明内容已持久化；保留保存后截图和结果。
6. 超时或响应不明时标记 `SAVE_UNCERTAIN`，先只读检查是否已落库。未确认前不连点保存、不自动新建第二单；找不到确切单据时交接具体缺口。

建议结果状态：`SUCCESS_FILL_ONLY`、`SUCCESS_DRAFT_SAVED`、`NEEDS_INPUT`、`READBACK_MISMATCH`、`SAVE_UNCERTAIN`、`WAIT_HUMAN_LOGIN`；仅有确切持久化与未提交状态证据才能返回 `SUCCESS_DRAFT_SAVED`。

验收：无保存授权、回读不完整、金额不闭合、必填缺失、错误页面或复合按钮均不能触发保存；保存响应不明不会制造重复单。真实验收须有用户指定的模板单号与材料，以及该具体任务的保存授权。缺少这些输入时先完成代码与离线验证，明确真实验收未完成。

### 阶段四 固化 skill 与交付完整试单

1. 更新 `.claude/skills/bpm-fill-run/SKILL.md`：日常入口支持“模板单号＋材料目录＋本次说明＋保存要求”，按需加载差旅资料，明确已支持分支与缺项处理。
2. 更新 README、AGENTS 的过时入口、耗时与授权描述；保留保存前核验和提交禁令。更新不得扩大到未授权上传、贴票或接口写入。
3. 提供新的差旅类型资料、计划约定、CLI 示例和实际验证记录；不改写已完成 workflow 的冻结合同与历史日志。
4. 在具备实际输入时跑一张端到端差旅单：精确读模板、本次材料生成计划、多表填写、独立回读、保存、重新打开核对、返回草稿等待审核。优先选择能覆盖本次扩展分支的真实任务，不凭空生成测试报销。

完成差旅真实试单后再接第二类型，优先考虑快递费。第二类用于检验配置与共享代码是否足够，不能仅增加配置就宣称填写已支持。

## 5 验证与协作规则

- 修改主探针后必须先执行 `python -X utf8 stage1_probe_selftest.py`，全绿后才能真实操作；新增多行、金额、身份及保存的语义验证，保持原有断言的保护目的。
- 离线场景围绕已发生的失败与保存门设计；修改不变量时说明为何仍保持原边界，不得为新功能删掉必要守卫。
- 同一 profile 页面操作串行，遵守已有锁与扫码门；不删活锁、不强关其他 session 的未保存页面。另一执行体只读分析工件可独立进行。
- events.jsonl 追加、每次 attempt 独立；计划与材料哈希绑定核验结果。凭证不进入普通工件、日志、报告或 git；业务敏感原值仅保留本地任务所需范围。
- 复杂建设沿用用户需要的 A/B 接力与独立审核方式；日常成熟填写走既定路径。独立审核须检查保存范围、无提交证据、金额条件与反例，而非仅看成功摘要。
- 不承诺所有单据 107.6 秒完成；分别记录材料解析、规划、页面填写、核验与保存耗时，以及人工介入原因。

## 6 最终交付标准

| 交付 | 完成依据 |
|---|---|
| 参数化入口和本单计划 | 新单不依赖旧 run、固定人员与旧计划；字段来源及缺项可追溯 |
| 多行执行器 | 各表按计划完整处理，不忽略超出旧样例的行，不默认换单 |
| 独立校验 | 能发现错值、跨表金额问题、多余/重复行及遗漏，不以固定 29/32 为标准 |
| 保存控制器 | 具体授权、保存前证据、精确按钮、未提交状态及持久化回读全部成立 |
| 任务结果 | 用户能用返回单号找到待审新草稿；提交、发送、流转零执行 |
| 失败交接 | 指明阶段、run/attempt、已填与已存状态、缺口和可恢复入口，不模糊宣称完成 |

报告能力时分别标注“代码已实现”“离线已验证”“真实填写已验证”“真实保存已验证”，未取得真实保存证据不得将目标流程标为全部完成。
