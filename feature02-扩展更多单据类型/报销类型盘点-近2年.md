## 一、技术路线

**目标**：按 制单人=运动表现研究部 拉取 BPM 报销单列表，枚举实际出现过的报销类别（submitType），近 2 年为主口径，为分类型 fill skill 定优先级。

**实现**：`list_type_query.py`（repo 根）——复用 `stage1_browser_probe` 的 profile 锁 / 浏览器启动（`--no-proxy-server`）/ 10h 登录态注入 / 扫码门 / 事件流落盘；不 import 任何填写逻辑，查询/翻页均过 NO_SAVE_WORDS 守卫（只填不存红线不破）。

**关键坑**（2026-10-23 上午 2 轮失败换来的，改脚本前先读）：

1. **PrimeNG 滚动表拆表**：表头表有 `prop-*` thead 但 tbody 空；表体表带全部行却无 thead → 行提取两步走（先从任一含 submitType 的 thead 取列序 props，再扫所有表的 tbody 按下标映射）。
2. **Angular 异步挂载**：goto 后定睡 3s 读表不稳（两轮实证 0 行）→ `wait_for_selector("th.prop-submitType")` + 1.5s 沉降。
3. **组织筛选控件**：readonly input 不可输入，触发器是 `button[aria-label='选择组织']` → `p-dialog.org-select-dialog` 内搜索选节点后点确定。

**流程**：登录态直注（免扫码）→ 列表基线 → 制单人=部门（失败回落申请部门）→ 查询 → 翻页采集全部行（按单号去重，24 页 469 行零丢失）→ 本地按制单日期 cutoff 分近 2 年 / 全量两口径聚合。

**复跑**：`python -X utf8 list_type_query.py --dept <部门>`（cwd=仓库根；换年限改脚本内 cutoff）。

## codex 接手：仍旧缓慢

核心原因是：这次演示仍在现场调试执行器。每遇到一个真实控件差异，就要由模型观察页面、修改代码、再尝试，耗时因此不断累积。

我查看了当前演示的运行日志 (/D:/Downloads/Mc Claude Code Workshop/2026-Auto-Pilot 企业微信/automation/runs/20261023-live-complex-demo/events.jsonl)。截至 17:18:21：

- 从启动已过去约 14 分钟，出现 10 次命令错误。
- 17:08 开始填写后，约 10 分钟仍在处理关联单据区块。
- 登录态已成功注入，主要卡点集中在控件操作。

具体有三个原因：

1. 真实控件适配尚未完成。
   关联类型选择器打不开或选项定位失败；单号选择后未正确确认回显；“本次报销”被当成普通输入格，实际需要填写下方关联明细，再由系统汇总带出。这些都在日志中实际发生了。
2. 一次失败引出一轮模型交互。
   当前使用任务目录里的临时驱动和补丁，已经产生二十多次命令响应。每轮包含观察、判断、写补丁、工具调用和等待；期间还有一次关联单替换授权确认。这种方式适合探索，日常填写会很慢。
3. 离线测试覆盖与真实操作之间存在缺口。
   此前多行测试用夹具模拟了选择器和系统回显，没有完整验证真实关联、预算及银行弹窗。因此 85 项测试通过，仍不足以证明整套现场操作成熟。这也是之前建设中应当更早补上的验证。

接下来最有效的做法是：先把当前遇到的关联类型、精确选单、关联明细金额填写三个动作逐一验证稳定，固化进共享执行器，再连续完成整单。 同一种失败应先查清原因，避免不断添加临时补丁重跑。

现阶段优先减少失败和模型往返。600ms 等待、失焦和回读应保留；直接压缩这些等待，解决不了当前主要耗时。

     chain.py（它的文档写明“真实用户供料走 fill_once
     正常任务流”）。我在 FASTLANE 计划 §1 里已明确：贯通执行器不经
     chain 实施，两者是并行的路，不是上下游。
  2. 唯一可能让新类型“惊动”引擎的情况：出现现有四~五表模型装不下的结构
     性新差异（当年研发的 products
     表就是）。那种情况动的是表模型和配置，也不是 runbook
     与调度器冲突——runbook 该写还是照写。

  结论：“每类型独立 runbook”的路线与贯通执行器正交互补——runbook
  越分越细没关系，引擎始终只有一套；反过来，引擎贯通后，每种 runbook
  的执行段自动继承“单浏览器一跑到底＋自动保存＋保页终审”的体验，新类型
  手册不用各自实现一遍。

## 10-29 技术路线 【windows-MCP】 vs 【playwright】

>> 通俗解释下【windows-MCP】和【playwright】两种路线的区别、优劣势

● 两条路线的本质区别一句话概括：Windows-MCP 是“派机器人坐在电脑前替你点鼠标”，Playwright 是“直接钻进网页内部跟代码对话”。

  打个比方

  把企业微信 OA 想象成一家餐厅：

  - Windows-MCP 路线：机器人坐在你的电脑前，隔着玻璃看这家店——它靠“无障碍朗读”（屏幕阅读器给盲人用的那套接口）听出哪里有按钮、哪里有输入框，记下它们的屏幕坐标
    ，然后伸出机械手按坐标去点。整个过程中你的电脑屏幕必须让给它（窗口必须在最前面），你本人不能碰。
  - Playwright 路线：程序自己开一个浏览器，直接走进餐厅后厨——网页里每个输入框都有名字（DOM
    选择器），它按名字喊人、直接填值，不需要“看”屏幕，也不需要占你的桌面。填完还能把整张表读回来核对，因为数据和它看到的是同一份。

  逐项对比

  优劣势总结

  Windows-MCP 的价值在“通用”和“探查”：
  - ✅  不管什么桌面软件都能碰一下；不用解决登录问题。
  - ❌  慢、占机器、坐标脆弱、读 CEF 内嵌网页还要打补丁——当生产主力很勉强。

  Playwright 的价值在“精准”和“量产”：
  - ✅  快、稳、可后台、可断言、数据全值回读——天生适合每天重复填单的生产线。
  - ❌  只对网页有效；需要独立登录；万一哪天 OA 封锁独立浏览器（指纹检测之类）就整条路断掉。

  为什么你们的项目最后是“Windows-MCP 探路、Playwright 施工”

  这正是两条路线互补的教科书案例：

  1. 企微 OA 藏在 CEF 壳里，一开始没人知道它“本质上是个网页”——是 Windows-MCP 探查时从无障碍树里挖出了完整 URL（bpm.qiaodan.com/...），Playwright
     路线才有了入口。探查阶段它的通用性不可替代。
  2. 入口找到后，验证“独立浏览器扫码能登录”成立，生产自然切到快而稳的 Playwright——慢 20 秒一次快照、独占前台这种特性，填一张 54 按钮 22
     表格的报销单是不可接受的。
  3. Windows-MCP + IA2 补丁退役为已验证的备胎：哪天 Playwright 路被 OA 封了，桌面路线当天可重建。
