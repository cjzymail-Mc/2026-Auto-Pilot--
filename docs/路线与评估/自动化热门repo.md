### 2. 对原先技术判断的修正

**截图驱动的视觉闭环是主流路线之一，但通用性不要求每一步都用鼠标。** 同一个通用代理可以按任务选择 API、浏览器页面结构、Windows 控件树和视觉定位。UFO 的现行文档已经明确描述 GUI 与原生应用 API 的混合执行。这里的“通用”体现在能跨应用完成任务；底层调用专门的执行工具并不会使代理失去通用性。[UFO 混合执行文档](https://github.com/microsoft/UFO/blob/main/documents/docs/ufo2/core_features/hybrid_actions.md)

**UIA 是否更稳，取决于目标控件是否被应用正确暴露。** 能看到企业微信主窗口，不代表能看到其内嵌 OA 表单的字段和按钮；UIA 通常也不能凭空读取未暴露的自绘控件。UFO 自己区分 UIA、OmniParser 视觉检测和二者混合三种后端，因此“UFO 是只走 UIA 的方案”也不准确。该报销单页面究竟属于哪种情况，目前缺少本机控件树实测。[UFO 控件检测文档](https://github.com/microsoft/UFO/blob/main/documents/docs/ufo2/core_features/control_detection/overview.md)

**代理框架、模型和执行工具应分别验收。** 截图工具正常，不代表模型收到了图片；模型能描述图片，不代表它能输出可用坐标；点击工具返回成功，也不代表页面进入了目标状态。最新会话中断在其中一环，不能把所有问题归因于模型推理能力，也不能用增加截图次数代替定位质量的验证。

### 4. 针对这台电脑，我建议按这个顺序推进

**第一步：做一次能力探查，再决定执行后端。** 先绑定企业微信目标窗口，读取窗口身份与控件树，检查是否能拿到“报销单”、字段标签、按钮名称、控件类型、启用状态和边界。首轮建议用 Windows-MCP；如果需要更严格的窗口快照绑定、后台执行或跨平台工具层，再对照 Cua Driver。若两者面对的是同一个未暴露控件的页面，反复更换 UIA 包装层通常不会增加信息。

**第二步：判断这个 OA 页面能否走浏览器结构化路线。** 如果有正常的浏览器入口且登录、单点认证和功能都成立，可用 Playwright／Playwright MCP 读取页面结构并按标签、角色、表格行列定位。这条路线值得优先评估，但不能假定企业微信内嵌页面能直接被接管，也不能假定新开浏览器会自动继承登录态。Playwright MCP 的现有浏览器连接有专门的扩展或端点条件。[Playwright MCP 文档](https://github.com/microsoft/playwright-mcp)

**第三步：结构不可读时，再进行纯视觉对照实验。** 选 UI-TARS Desktop，先在简单页面验证“截图能进入模型 → 模型能定位 → 工具能执行 → 新截图能确认结果”，再测试企业微信 OA。若继续由 GLM 规划，视觉定位也可以交给独立工具／模型，但要先验证端点成功率和图片传输；不要继续围绕持续返回 500 的同一服务堆叠临时脚本。

**第四步：稳定任务再固化，跨应用任务再升级。** 单个页面探索没有必要先引入完整的 AgentOS。等字段、导航、验证条件明确后，将重复步骤固化为 UIA／浏览器工具；确实需要“取文件 → 整理表格 → 操作多个桌面应用”等长流程时，再评估 UFO 的编排与混合执行能力。

如果后续发现有该 OA 系统正式支持、已经授权的业务 API，可让批量读写走 API，并用界面核验结果；企业微信本身有 API，并不能推出第三方 OA 报销单也能通过它填写。当前没有足够证据推荐这条业务 API 路线。

### 5. 无论选哪个项目，都应补齐的闭环

| 环节 | 最少应满足的条件 |
| --- | --- |
| 观察 | 绑定目标窗口和截图时点，记录窗口大小、截图缩放和坐标基准；能区分目标页、终端与资源管理器。 |
| 定位 | 优先使用带角色／名称的结构化元素；视觉或 OCR 定位要保留完整边界和上下文。现有 OCR 主要输出一行首个词的左上角，这还不足以直接代表目标控件的点击区域。 |
| 执行 | 同一桌面上的切窗、截图和输入按闭环串行进行；布局变动后重新定位。不要让不同代理同时操作同一窗口，也不要对旧截图中的坐标连续发动作。 |
| 验证 | 联系人任务检查打开后的聊天标题；表单任务检查目标区块、字段状态及动作前后的差异。工具返回“已点击”只能证明发送了输入。 |
| 恢复 | 服务故障与“目标不存在”分别处理；重复失败后切换信息源或停止并说明。需要恢复视图时，按位置／锚点核验恢复，不能假定正反相同次数的滚轮事件会严格抵消。 |

针对当前报销单探索，已经识别到的 `+`、保存、发送等入口不应作为只读试验目标。折叠箭头和新增行按钮也要先区分清楚，不能把图标含义当作已经验证的事实。

### 6. 建议的最小验收任务

把同一个任务交给候选方案：**识别当前报销单页面，列出主要字段和区块，区分表头、按钮和新增行入口，完成一次有必要的只读导航并验证结果。** 先做 3～5 次重复试跑，其中至少一次使用不同窗口宽度，比较：

1. 是否始终绑定正确窗口，是否混入其他应用的内容。
2. 是否能区分文字与可操作控件，是否明确报告无法确定的项目。
3. 是否在每次动作后验证预期状态，而不是只记录输入事件成功。
4. 总耗时、模型调用次数、错误定位次数和人工纠正次数。
5. 模型服务不可用时，是否能合理降级并保留可核对的证据。
