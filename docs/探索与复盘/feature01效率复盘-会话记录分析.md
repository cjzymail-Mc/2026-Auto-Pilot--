# 二、原理:这条链路是怎么跑起来的

```
Claude 主循环 / Workflow agent
   │  Bash: python wmcp_probe.py chain steps.json     ← 自写 stdio 探针(JSON-RPC,UTF-8 落盘防 GBK)
   ▼
Windows-MCP v0.8.8 (MCP server, uv 托管 Python 3.14.7)
   │  tree/service.py 已打本地 CEF 补丁(三处 IA2 合并分支)
   ▼
两条 Windows 无障碍 API:
   ├─ UIA (pywin32) ──────────┐
   └─ MSAA/IAccessible2 ──────┴─→ CefBrowserWindow → Chrome_RenderWidgetHostHWND
                                   (Chromium 无障碍树是惰性的,被查询"敲门"才构建)
   ▼
返回:控件树文本(名称+值+物理像素坐标)→ 写文件 → LLM 用 Grep 搜行、算坐标
   ▼
行动:Click {"loc":[x,y]} / Type(长中文走剪贴板)→ 再 Snapshot 前后对比确认
```

**本质:用 LLM 的"思考-工具"循环,串行地模拟一个屏幕阅读器在操作 GUI。** 每填一个字段 = 感知(全桌面树快照,几百行)→ 定位(搜行取坐标)→ 行动(点击/输入)→ 再感知(验证),一个字段的闭环就是 2-3 个完整模型轮次,每次都重读整个对话上下文。约 15 个可填字段 × 大量失败重试 ≈ 113 条链。

# 三、为什么效率低——六层原因(按权重排序,v2 修订)

**1. 感知-行动循环放在了 LLM 里,而它天生串行且每步都"重新看世界"**
这是根因。桌面是独占资源:Snapshot 要求企微必须前台、Click 必须与 Snapshot 同一 server 会话——所以用户要的 workflow 并行化在这个任务上**天然无效**(两个 agent 同时点鼠标=灾难)。Workflow 只能加速 OCR/验证等旁路,主填单循环仍是单线程的"快照→思考→点击→快照"。**10-21 上午的段落数据进一步证实:352 条消息全部是主循环裸跑(零 Workflow、零 Task),节奏与昨天无异,效率没有任何改善。**用户"不惜 token 换效率"的授权,换不来不存在的并行度。

**2. 8 次上下文压缩 = 8 次战术失忆**
每次压缩丢掉:已验证的坐标、已失败的尝试原因、安全红线清单、工具怪癖。于是反复重学同样的课——最典型的一例:`[09:23] 证实金额是表内汇总字段,难怪 6 次 typing 都不落`,对着一个**自动计算字段**白白打了 6 轮。压缩→重推导→更多轮次→更快再压缩,是负反馈死循环。上午 C 表列位(报销项目490|摘要590|预算部门790|…)在 10-21 被重新逆向了一遍,而同类"列头图破译"昨天就做过(09:21 序号468|科目504|摘要593…)——**两次压缩之间连表结构这种硬知识都没守住**。

**3. 绝对像素坐标天然脆弱,并已造成真实数据事故(v2 新增,权重上调)**
10-21 10:21 `[02:21] 事故!链中途页面上移了~100px,Type 全打进了银行行`:页面在链执行中途滚动/位移,快照时代理记下的绝对坐标全部失效,输入串行污染了错误字段——银行**账号被写成"2026-09-22"**、**转账金额被写成行程说明**。随后是清点损失(r118 前后多轮快照比对)+ 修复重填。这不是偶发操作失误,而是"快照→坐标→行动"架构的**系统性缺陷**:坐标在采集与使用之间没有任何锚点校验,布局一变就静默打错位置。DOM 选择器/无障碍节点引用路线不存在此问题。

**4. 关键知识只能靠试错获得,且没有沉淀成 skill**
"Click 与 Snapshot 须同会话""企微必须前台""下拉要走选择器弹窗而非直点""控制台 GBK 只能落盘再 Read"……每条都是 2-5 次失败换来的。会话里两次 Workflow 脚本的 `KNOW` 块和最终 memory(`wecom-oa-ia2-accessibility`)是事后的沉淀,**冷启动时不存在**。

**5. 双重环境摩擦放大每一步成本**
Windows 控制台 GBK 乱码 → 所有中文输出必须写文件再 Read(工具轮 ×2);每条 Bash 输出前还垫一行代理横幅;截图/裁剪/放大 OCR 全靠现写 PowerShell 脚本(目录里 20+ 个 ps1,上午还在新增 `click_ocr.ps1`)。

**6. 路线本身的权重错配**
报告其实早就指出了捷径:IA2 树的 document 节点直接暴露了 OA 真实 URL(`https://bpm.qiaodan.com/oa/reimburse?type=new`)——**同一个表单用 Playwright 开真浏览器**就是 DOM 选择器问题,无快照、无前台要求、无坐标试错、无位移事故。但会话选择了在 CEF 无障碍树上硬啃,等于用最贵的方式做免费的事。两天 113 条链、77.5M token 之后,连表单字段都还没认全——**路线成本不是线性难受,是不收敛**。

# 五、如果重来一次(结论性建议,v2 修订)

1. **把循环下沉到确定性代码**:写一个 Python 驱动器(字段→定位规则→动作表),链内自动跑"快照-匹配-点击-验证"N 轮不经过模型;LLM 只做规划和异常处理。113 条链里至少 90 条本可以零 token 完成。
2. **立即止损换路线**(v2 升级为最高优先):`bpm.qiaodan.com` 的 Playwright 入口早已拿到,DOM 自动化能让整个任务从 8+ 小时/77.5M token 掉到分钟级。10-21 的坐标事故证明 CEF-IA2 链路不仅贵,而且**不安全**(打错真实企业数据字段)。除非未来某天绝对禁止开浏览器,否则没有理由继续。
3. **若必须留在 IA2 路线:坐标用锚点相对化**(每次行动前在链内先取参考控件坐标再换算),并把"链执行前校验锚点未位移"写进驱动器——把 10-21 事故类风险挡在模型层之下。
4. **把 KNOW 块升级为正式 skill**(操作序列、安全红线、坐标禁忌、工具怪癖、表结构字典),让每次压缩/新会话零成本继承——上午重学昨天表结构的 2 次压缩学费,本可全免。
