## 3. P1：在扫码前修好最小探针

目标文件：[stage1_browser_probe.py](../stage1_browser_probe.py)。先完成下表，随后才运行登录后的分支。

| 缺口及代码位置 | 最小修复 | 验收条件 |
|---|---|---|
| 第 17 行把 RUN 写死为旧 run | 接收或生成新的 run ID；每次尝试放入独立 attempt 目录。结果文件原子写入 | 重跑不覆盖旧 `stage1_result.json`、截图、HTML 或日志证据 |
| `phase()` 捕获异常后继续；主流程最终仍可能 `DONE` | 阶段返回明确状态；必需阶段失败立即结束依赖它的后续阶段；整体成功由业务断言计算 | 模拟定位失败后，结构和恢复阶段不执行，最终状态为失败或阻塞 |
| `classify()` 用导航关键词数量认定登录 | 登录判断同时核对域名、登录页退出状态及实际账户/组织标识；身份未确认时保持 UNKNOWN | 无账户证据的普通页面不能判成登录完成 |
| `locate()` 没有确认指定单据；找不到目标仍返回 ok | 输入明确的目标身份；检查实际列表、候选数量、筛选范围与匹配结果 | 找不到或出现多个候选时停止，不进入另一张单据 |
| `structure()` 找不到查看入口就打开 `type=new` | 移除自动新建页回退；只检查已确认的现有目标。确需空白表单测试时另立明确目标和动作范围 | 只读恢复任务不能悄悄变成新建表单探索 |
| `recover()` 只 reload 并返回 ok | 对已保存且已确认的目标，在刷新前后比对单据 ID、账户、状态及关键值；另做浏览器重启后的登录态验证 | 登出、打开别的单据、关键值改变，都不能通过恢复验收 |
| `WALL_CAP` 未使用，`budget_left()` 只打印 | 使用单调时钟检查预算，限制每次等待，并设置能终止卡住操作的看护机制 | 超时有实际停止行为；结束前确认旧执行已退出 |
| 结构扫描只看主文档，主要统计控件数量 | 枚举相关 frame，识别具体表格、行、列和编辑器；保存少量确定字段的实际读取结果 | “发现 table/input”不能代替“正确读到了指定字段” |

将六个检查项都初始化为明确状态，例如 `NOT_RUN / PASS / BLOCKED / FAIL / NOT_AUTHORIZED`，附带原因和证据路径。没有执行的检查不得缺省成通过。

只读导航采用已核实的目标和允许范围，不能用“没有调用 fill/click”代替动作含义检查。当前 `WRITE_BTN` 是未接入的变量，不能在报告里将它描述为已生效的保护。

- 保留本机已验证的绕代理参数，不修改系统代理。

**本阶段验收：** 离线覆盖“定位失败、身份不符、预算耗尽、证据目录冲突、恢复到错误单据”等有实际意义的失败场景；不需要用通用流程测试数量代替这些用例。

## 4. P2：用户在场时扫码，完成真实只读验证

探针修好后，安排一次连续执行：

1. 启动新 run 的受控浏览器，展示新二维码，提示用户在该窗口完成扫码。
2. 检测二维码过期并给出明确状态。旧截图已显示“二维码已过期”，不能把整个 480 秒等待窗口都当成二维码有效期；必要时刷新登录组件，不操作企微原表单页签。
3. 扫码完成后，核对正确账户与组织，确认进入 OA 内部。
4. 通过正常列表入口定位目标。已有快照证明列表路由是 **`/oa/reimburses`**；当前 schema 把它写成了 `/oa/reimburse`，应纠正，并以实际页面导航再次核实。
5. 读取目标单据身份和几个代表性字段，建立字段、所在区块、行身份、显示值之间的对应关系。
6. 如果目标是已保存单据，验证刷新后仍为同一单据；关闭并重开受控浏览器后，再验证登录态和目标可恢复。未保存的企微原表单不参与破坏性刷新试验。

本轮字段范围保持小：一个普通文本字段、一个复杂选择器或表格单元格、一个计算字段，以及必要的账户和单据身份字段。先证明它们能正确定位和读取，再扩到整张表。

若没有可定位的已保存草稿，分别交付：当前未保存内容的基线、已覆盖的草稿查询范围、缺少的目标条件。不要自动创建新单或选择第一张历史单据顶替。

**本阶段验收：** 登录身份已确认；目标单据明确；代表性字段具有实际定位和回读证据；恢复检查确实比较了同一对象。成功后才将路线状态提升为“浏览器只读验证通过，写入待验”。

## 5. P3：把字段初稿收敛为可执行的局部配置

先修正 [form-schema.json](../automation/form-schema.json) 的这些问题：

- 列表 URL 改为已核实的真实路由。
- “可写”不要混用布尔值和 `PENDING(...)` 字符串；使用明确枚举，例如 `READ_ONLY / WRITABLE / UNKNOWN`，把授权范围单独保存。UNKNOWN 一律不能进入写入动作。
- 展示序号不直接视为稳定行键。确认真实记录标识，或使用能唯一匹配、且可在现场重新校验的业务组合键；排序、插入或删除后重新绑定。
- 一条字段记录对应一个明确字段，拆开当前用斜杠合并多个业务字段的条目。
- 只有实测过的定位和校验才标记 VERIFIED，其他条目继续保留待验状态。

下一轮只完成上述代表性字段的配置，不以“消灭全部 PENDING”为目标。完整字段适配应建立在可靠的局部执行方式上。

## 6. P4：获得明确写入目标后，验证两个字段

沿用会话中已有的明确授权；缺少目标或允许动作时，只补齐缺失部分，不重复询问已确认的范围。当前这份计划本身不授权 OA 写入。

有了可写的测试目标后，依次验证：

1. 一个普通字段：核对原值 → 输入 → 失焦 → 等待页面处理 → 回读 → 比较。
2. 一个困难字段：确认区块和行身份 → 打开选择器或编辑器 → 唯一匹配 → 操作 → 回读。
3. 一个失败场景：目标不唯一、编辑器身份不符或回读不一致时，程序停止后续写入。
4. 一个中断恢复场景：重新进入后先核对现场，不能重复加行或覆盖已有非预期内容。

保存、上传、提交分别记录状态，并分别遵守已有授权。通过这些验证后，再扩展最小执行器、运行状态和整单字段。
